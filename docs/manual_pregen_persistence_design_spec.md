# 設計規格：手動預製角色跨遊戲保存

## 問題與目標

手動上傳 `role_` 角色卡後，角色會與劇本抽取的預製角色比對並擇優融合。融合結果目前寫入 `GroupState.pregens`，因此只跟著當前遊戲狀態保存：選擇其他劇本會以該劇本的 `pregens.json` 取代角色池，`/coc newgame` 會建立全新的 `GroupState`。同一團再次遊玩時，手動角色卡和融合資訊因而需要重新匯入。

本功能讓手動角色卡及其融合結果可在同一 Discord 群組內跨 `/coc newgame` 與劇本切換保存，並在載入對應劇本時還原到可認領的預製角色池。保存資料以群組和劇本為範圍，避免污染所有群組共用的劇本庫。

## 範圍與非目標

### 範圍

- 持久保存群組手動匯入的原始角色卡，載入時重建與劇本抽取角色的融合結果；無法還原來源的舊 merged 卡另以受來源版本限制的 snapshot 過渡。
- 依 `(group_id, scenario_id)` 隔離保存；同一角色卡不自動分享給其他群組。
- 選用已知劇本時，將劇本庫預製角色與該群組、該劇本的手動角色資料合併，形成當局 `GroupState.pregens`。
- `/coc newgame` 清除當局遊戲進度與認領狀態，但不刪除已保存的手動角色卡。
- 保留目前「手動角色卡與劇本內建角色不論上傳先後皆能比對融合」的行為。
- 定義使用者明確移除持久角色資料的操作；預設可納入 `/coc pregens` 的移除子命令或獨立管理命令，實際指令名稱在實作前定案。

### 非目標

- 不將某群組的手動角色寫入共用劇本庫的 `pregens.json`。
- 不保存已認領角色的遊戲中狀態（HP、SAN、Luck、彈藥、物品、當前傷勢等）；這些仍屬於 `GroupState.characters` 與遊戲存檔。
- 不改變角色比對演算法、欄位擇優規則或 LLM 抽取方式。
- 不將角色卡跨群組分享，也不提供雲端匯出／匯入功能。

## 名詞

| 名詞 | 定義 |
| --- | --- |
| 劇本預製角色 | 從所選劇本抽取並存於共用劇本庫 `pregens.json` 的角色。 |
| 手動角色資料 | 群組成員以 `role_` 檔案匯入，由固定格式解析器產生的角色資料。 |
| 持久角色池 | 依群組與劇本保存、可供後續遊戲重新建立角色池的手動角色記錄。 |
| 當局角色池 | 當前 `GroupState.pregens`，包含已與劇本角色融合、可供認領的角色。 |

## 持久化模型

新增獨立的持久角色資料表／repository，不把跨遊戲資產僅放在 `GroupState`，也不放入共用劇本項目。現有 `app/db.py` 採固定表名、每列一個 JSON blob 的鍵值表；本功能沿用該慣例，新增 `manual_pregen_assets` 到 `_TABLES`，不另建不同形狀的關聯式表：

```text
table: manual_pregen_assets (key TEXT PRIMARY KEY, data JSON, updated_at TEXT)
key: JSON array [group_id, scenario_id]
     scenario_id = null 表示尚未綁定劇本的群組角色卡
data: {
  "schema_version": 1,
  "entries": [
    {"asset_id": "穩定 UUID", "filename": "role_...md", "pregen": {"source": "manual", "...": "..."}}
  ],
  "legacy_snapshots": [
    {"asset_id": "穩定 UUID", "source_hash": "原 PDF 內容雜湊", "pregen": {"source": "merged", "...": "..."}}
  ]
}
```

`scenario_id` 使用穩定的 Scenario Library ID；key 用 JSON 編碼避免群組 ID、劇本 ID 字串拼接碰撞。`asset_id` 第一次匯入時產生，更新時保留。`entries[*].pregen` 保存**未融合的原始手動卡**，只含重建角色池所需欄位，不含 `claimed_by`、玩家骰出的 Luck 或即時 HP/SAN/裝備狀態。新資料的融合結果是載入時的衍生資料，不另外當成手動來源保存；否則劇本重新解析後可能把舊 PDF 數值誤當成手動欄位，覆蓋新資料。`legacy_snapshots` 僅供舊版 `source: "merged"` 遷移：它不是人工來源，只能在原 PDF `source_hash` 未改變時原樣還原；重新解析後標為過期並請 KP 重新匯入原始卡。

重傳具名角色卡時，先用現有 `character_matcher.is_same_character` 比對同範圍的手動資產，命中則原位更新並保留 `asset_id`；相同檔名且角色姓名仍空白的卡，視為同一資產更新。若兩張不同角色卡使用同名檔案，需改名再匯入，避免覆蓋；回覆訊息須顯示資產 ID 與更新／新增結果。持久資料只保留一份最新版本，不提供同一劇本多組名單。

角色比對沿用 `character_matcher.is_same_character` 與 `reconcile_pregen_into_pool`。若劇本重新解析、內建角色資料改變，載入時仍以目前劇本庫版本為基礎，重新套用該群組保存的原始手動資料。欄位優先序沿用現有融合規則：人工角色卡明確提供的屬性、衍生值、背景和技能優先，劇本抽取內容可補足人工卡未提供的祕密動機等資料。LUCK 仍以**最後融合後**的卡面值判斷；群組資產不記錄玩家開局擲出的 LUCK（見 [PR #84](https://github.com/marcoliu99/line-coc-keeper/pull/84)）。

## 流程

### 匯入角色卡

1. 解析 `role_` 檔案並載入目前群組狀態。
2. 若目前有有效的 `scenario_library_id`，將未融合的手動資料寫入該 `(group_id, scenario_id)` 資產，再以當前劇本庫角色與此資產重建 `GroupState.pregens`。重傳同一張卡只更新對應 `asset_id`。
3. 若尚未選定可識別的劇本，先寫入 `(group_id, null)` 待綁定區，並繼續在當局角色池顯示；首次**明確**選用劇本或首次 PDF 匯入成功時，把待綁定資產移到該劇本範圍並重建融合結果。若已有同角色資產，依上方更新規則去重。不能把待綁定卡自動混入之後每一個劇本。
4. 持久資產與當局 `GroupState` 必須在同一資料庫交易提交；失敗時兩者都不更新，也不回覆「已保存」。回覆新增、更新或融合結果及資產 ID。

### 選用劇本

1. 讀取共用劇本庫的劇本預製角色。
2. 查詢目前群組和該劇本 ID 的持久角色資料。
3. 從乾淨的劇本庫角色複本開始，依 `asset_id` 穩定順序套用手動資產，以現有角色比對／融合邏輯建立當局角色池；清除持久資產及新角色池中的舊 `claimed_by` 狀態。不要直接修改共用劇本庫物件。
4. 保存 `GroupState`。另一群組選用同一劇本時只讀取自己的持久角色資料，不會看到本群組手動角色。

### `/coc newgame`

`/coc newgame` 仍重建當局 `GroupState`、清空角色認領和出戰狀態，但不刪除持久角色 repository。之後須明確執行 `/coc scenario use <id>` 或重新匯入劇本，才依選定的 `scenario_id` 還原對應角色池；不從舊群組狀態猜測要恢復哪個劇本，也不自動開始遊戲。

### 更換或重新解析劇本

- 選用不同劇本只載入新劇本和該群組對應的手動角色資料；舊劇本資料留存，日後切回可再次載入。
- 重新解析同一劇本不清除持久手動角色資料。重新融合後，劇本抽取結果更新，但手動填寫欄位仍依既有優先序保留。
- 清除共用劇本庫項目是否連帶清除各群組持久角色資料：預設不連帶清除，避免共享資產管理操作刪除私有玩家資料；提供獨立明確刪除操作。

### 管理與刪除

提供 `/coc scenario cards list <scenario_id>` 列出本群組對該劇本的手動資產 ID、角色名與檔名；`/coc scenario cards delete <scenario_id> <asset_id>` 僅刪除指定資產，接著由劇本庫角色與剩餘資產重建未認領角色池。若該資產對應的當局 pregen 已被認領，拒絕刪除並提示先結束／重開新局，避免把已認領角色重新列為可選；不能改寫即時 `Character`。兩個指令只允許目前 KP Assistant 或 Discord Keeper 執行。本期不提供「一次清空全部角色卡」命令，降低誤刪風險；同名角色以 `asset_id` 消除歧義。刪除持久資料與更新當局角色池同一交易提交。共用 `/coc scenario clean` 不連帶刪除群組資產；劇本再次建立新 ID 時，舊資產也不會按標題自動接到新劇本。

## 資料生命週期與安全邊界

- 資料擁有者是 Discord 群組，不是單一上傳者；符合目前群組角色池行為。
- `scenario_id` 是持久化關聯鍵。沒有有效劇本 ID 時只進待綁定區，不以劇本標題或檔名猜測綁定。
- 持久角色資料不得含已認領玩家角色的即時數值或遊戲進度。認領後 `GroupState.characters` 是執行中角色的唯一權威來源。
- 持久層每次寫入需與角色匯入／融合結果保持一致。現有 `save_state()` 會自行開啟交易並執行 `state_revision` 檢查；實作需抽出可共用的同交易保存邊界，在相同的群組 state lock、revision 檢查及 `BEGIN IMMEDIATE` 下，以 `db.set_json_tx()` 一起寫 `manual_pregen_assets` 與群組狀態。不能先 `db.set_json()` 再 `save_state()`，否則後者失敗會留下半完成結果。
- 依目前資料備份策略納入 SQLite 備份；記錄必要的資料版本以供未來 schema migration。

## 相容性與整合

- `GroupState.pregens` 仍是 `/coc pregens`、`/coc usepregen` 的當局讀取介面，不改動呼叫端的主要語意。
- 共用 `scenario_library` 僅提供劇本原始角色；群組私有角色資料由新的 repository 在劇本載入時疊加。
- 舊群組狀態裡 `source: "manual"` 的未認領卡可以自動遷移成原始手動資產：有有效 `scenario_library_id` 時綁該劇本，否則放待綁定區，依 `asset_id`／內容指紋檢查冪等性。`source: "merged"` 已混入 PDF 欄位，無法可靠還原原始手動卡；不可悄悄當作人工來源重複融合。有有效劇本 ID 及來源雜湊時，將其保存為 `legacy_snapshots`，讓同版劇本在下一局可繼續選用；劇本來源變更後不套用過期 snapshot，而提示 KP 重新匯入原始 `role_` 檔案。不自動改寫已認領角色。
- 需要檢查直接 PDF 上傳、Scenario Library `use`、PDF 修正／重解析，以及 `/coc newgame` 各條路徑，確保都呼叫同一個角色池載入／持久化邊界。

## 相鄰需求：RAG 中文模板持久保存

RAG 中文模板的持久化已有獨立實作於 [PR #83](https://github.com/marcoliu99/line-coc-keeper/pull/83)，目前仍在 PR 審閱，**不納入本功能的資料表或實作範圍**。它與手動角色池有不同的資料擁有者與生命週期：中文模板是多群組共用的劇本衍生資產，手動角色卡則屬於單一群組與劇本。

- 原文劇本仍是權威來源；中文模板作為可重建、可審閱的 RAG 衍生版本與原劇本並存，不覆寫原文。
- 預處理成功後將模板及其狀態寫入劇本庫。重啟服務、群組執行 `/coc newgame` 或切換群組，不應造成已保存模板遺失或要求重新產生。
- 群組選用哪個語言／模板版本屬於群組偏好，需以 `(group_id, scenario_id)` 綁定並跨 `/coc newgame` 保留；載入 RAG 時依該選擇讀取已保存模板。
- 重新解析或原始劇本內容改變時，以來源內容版本判斷模板是否過期；保留舊版供回退或比較，不可靜默把舊模板當成新內容的有效版本。
- PR #83 與本 spec 應分開遷移、清除及授權；若它先合入 `main_v2`，本功能的實作須以合入後的最新 `main_v2` 對齊。

## 測試計畫

- 同一角色卡匯入並融合後，重啟 repository／重新載入群組狀態仍可恢復角色。
- `/coc newgame` 後選回同一劇本，手動角色和融合欄位仍在，認領狀態已清除。
- 切到另一劇本時不載入舊劇本角色；切回原劇本時可恢復。
- 兩個群組使用同一劇本時，彼此手動角色資料完全隔離。
- 手動卡先於 PDF 上傳，以及 PDF 先於手動卡上傳，最後角色池相同。
- 同一手動卡重傳可更新既有持久資料，不產生重複角色；不同角色不因職業相同而錯誤合併。
- 同一劇本重解析後，重新抽取的劇本資料與人工優先欄位能按既有融合規則正確合併。
- 持久化寫入失敗時，指令不回報保存成功，且不產生不一致的部分寫入。
- 明確刪除群組／劇本的手動角色資料只影響指定的 `(group_id, scenario_id)`。
- 首次 PDF 上傳前已有待綁定 `role_` 卡時，PDF 匯入、劇本庫選用與 PDF 修正都能用同一邊界綁定／重建；待綁定卡不會流入之後切換的其他劇本。
- 新舊 `GroupState.pregens` 的 `manual`／`merged` 資料遷移可重複執行且不增生重複資產；舊 merged snapshot 同版可恢復、不同來源雜湊不可誤用。
- 手動資產和群組狀態的同交易提交：模擬 revision conflict 或寫入失敗時，兩邊皆無部分更新。
- 清理共用劇本庫不會刪掉群組私有資產；管理命令只能列出、刪除目前群組指定劇本的資產，不能修改已認領玩家角色。

## 審閱決策

本稿收斂成以下預設，待使用者審閱後才進入程式實作：

1. 同一群組、同一劇本只保留最新一組手動角色資產；重傳同一角色更新，不保留多版名單。
2. 待綁定卡在第一次**明確**選用或成功匯入劇本時綁定；不按標題猜測，也不流入其他劇本。
3. 只提供 KP 逐張列出與刪除的指令，本期沒有整批清空；刪除不碰已認領的玩家角色。
4. `/coc newgame` 後須重新選劇本才載入該劇本的角色池，沒有自動沿用上局劇本的快捷行為。
5. 舊 `merged` 卡因缺原始手動來源，只能在 PDF 雜湊未變時以 snapshot 恢復；來源變動後需重新匯入原始 `role_` 卡。這是避免把舊 PDF 值永久誤認為人工填寫值的取捨。
