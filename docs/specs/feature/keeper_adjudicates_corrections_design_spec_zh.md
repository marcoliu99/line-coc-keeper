# 群組沒有 KP 助手時，由守秘人裁定敘事更正

[English](keeper_adjudicates_corrections_design_spec.md)

狀態：**backlog**（等待規格審查）。基準：`bug/keeper-role-superuser` 的 `434b76d`。決策紀錄：`docs/adr/0001-keeper-adjudicates-corrections-without-kp.md`。

## 問題

玩家用 `/coc correct` 提報守秘人敘事的錯誤。提報只是**指控**：在有人裁定之前，不會改變劇情。只有 KP 能核准、駁回、擱置或取代它（`app/commands/handlers/correct.py`）。

不是每場都有 KP 助手，而守秘人是機器人。在沒有 KP 助手的群組裡，沒有人能裁定：提報會一直停在待處理，直到每群組上限（12 筆）或每位提報者上限（3 筆）擋住新的提報。`keeper` 身分組那條路看起來像出路，但它只對*擁有該身分組的真人*有效，而且正要被移除（`docs/specs/bug/keeper_role_superuser_design_spec.md`）。

## 規則（已和 Marco 確認）

- **群組有登記的 KP 助手：** 由那位 KP 助手（這個群組的 `kp_assistant_user_id`）裁定，和現在完全一樣。其他群組的 KP 助手不算；`quit`、`transfer` 或 `takeover` 之後，改由新的那位裁定。
- **群組沒有 KP 助手：** 由**守秘人**依證據裁定核准或駁回。
- **擱置**和**取代**仍然只有 KP 助手能做。它們會暫停工具、整理已核准的更正，屬於管理工作，不是事實裁定。

## 守秘人怎麼裁定

設計的前提不變：**提報者寫的內容永遠不是證據。**它只說明要檢查什麼，不代表什麼是真的。這樣才能防止玩家捏造更正（例如「守秘人說我找到了一把槍」），讓它變成正典。

1. **觸發：** 在沒有 KP 助手的群組建立提報，提報存檔並回覆確認之後，在背景啟動裁定。如果群組的 KP 助手解除身分（`/coc kp quit`），而仍有待處理的提報，也會觸發。（`transfer` 和 `takeover` 一定會產生新的 KP，所以不會觸發。）裁定**可以重試**：在沒有 KP 的群組裡，還沒有裁定結果的待處理提報，會在下一筆新提報或有人下 `/coc correct list` 時被重新處理，所以裁定途中機器人重啟也不會遺失。
2. **證據包：** 只用系統持有的資料：
   - 目標訊息收據裡的原文，也就是被指控的那則守秘人訊息（`narrative_message_receipts`，最多 2,000 字），以及它的 `state_revision` 和 `turn_id`；
   - 指控涉及的目前狀態事實：角色卡、物品、狀態、位置、線索、既定事實；
   - 透過既有檢索找到的相關劇本段落；
   - 該回合前後的近期回合紀錄。
   提報者的 `issue` 放在證據之後，另外**標示為未經證實的指控**。
3. **結構化裁定：** 透過 `registry.analysis_provider()` 做一次強制工具呼叫，回傳：
   - `decision`：`approve`｜`reject`｜`undecided`；
   - `evidence`：依據的具體項目；
   - `resolution`：只有核准時才有，是公開的更正內容，1–1000 字。
   輸出會像其他結構化分析一樣驗證，任何無效的輸出都當作 `undecided`。
4. **防護（在程式裡檢查，不只寫在提示中）：**
   - 只有證據和被指控的敘事**互相矛盾**時才核准，例如敘事提到調查員沒有的物品，或把狀態、劇本事實說錯。
   - 核准的更正不能新增證據裡沒有的物品、技能、HP／SAN／幸運、線索或事實；如果更正內容提到不存在的狀態，就退回。
   - 證據不足時，結果是 `undecided`，絕不猜測。
5. **結果：**
   - `approve`／`reject`：和 KP 裁定一樣存檔，另外記錄 `adjudicated_by: "keeper"` 和證據摘要，並公開貼出裁定和理由。
   - `undecided`：提報改為新的 **`unverified`（無法查證）**狀態，並告訴群組守秘人無法查證。`unverified` 的提報**不佔用**待處理上限（每群組 12 筆、每位提報者 3 筆），所以沒有 KP 的群組不會被填滿、讓大家都不能提報。它們仍會列出；之後登記的 KP 助手仍然可以裁定，提報者也仍然可以撤回。為了防止單一玩家不斷拿捏造的提報讓守秘人裁定，**每位提報者最多同時保留 3 筆 `unverified` 提報**，超過之後他的新提報會被拒絕，直到他撤回一筆或有 KP 處理。這只會擋住那一位玩家，不會擋住整個群組。已和 Marco 確認。
   - 每次裁定都記錄 `correction.keeper_ruling`（裁定結果、提報編號、證據種類），不記錄任何玩家文字。
6. **推翻：** 之後登記的 KP 助手，可以像處理任何已核准的更正一樣，**取代**守秘人的裁定。
7. **寫入裁定（避免競態）：** 模型呼叫在鎖外執行。裁定透過一般的鎖保護狀態變更寫入，而且只有在提報**仍是待處理**、時間線沒變、群組**仍然沒有 KP 助手**時才寫入。如果這段期間有人登記成 KP、提報者撤回，或遊戲換到別的時間線，裁定就放棄並記錄日誌。
8. **公開時不洩漏劇透：** 劇本段落和其他玩家的私人資訊，只是裁定用的證據，絕不寫進公開訊息。公開貼出的內容只有：裁定結果、更正內容（核准時），以及只用玩家已經看得到的東西（被指控的敘事和公開狀態）說明的理由。貼出前會用 `spoiler_policy.sanitize_public_text` 搭配 `collect_protected_terms(state)` 過濾；如果過濾會改動內容，就只貼出裁定結果和一般性的理由。完整證據只留在內部紀錄，不貼到頻道。

## 不在範圍內

- 守秘人*建議*登記的 KP 助手如何裁定。這可以作為後續功能。
- 由守秘人執行回溯、回溯節點或 sudo，也就是 `keeper` 身分組規格裡提到的其他裁決權。

## 測試

- **分流：** 有 KP 助手時不觸發裁定，KP 指令行為和現在一樣；沒有 KP 助手時，每筆新提報觸發一次裁定，KP 位子空出而仍有待處理的提報時也會觸發。
- **防話術操縱：** 沒有證據支持的捏造指控絕不會被核准。測試案例包括宣稱有物品、有線索、「守秘人說……」。
- **防護：** 核准內容若引入證據裡沒有的狀態，會被拒絕並改為 `undecided`。
- **結果：** 核准和駁回會以 `adjudicated_by: "keeper"` 存檔並貼出；`undecided` 維持待處理並發出通知；無效的模型輸出當作 `undecided`。
- **推翻：** 之後的 KP 可以取代守秘人的裁定。
- **擱置和取代**仍然只有 KP 能做。
- **競態：** 裁定進行中有人登記成 KP，或提報者撤回，裁定都會被放棄，什麼都不寫入；時間線改變時也一樣。
- **重試：** 沒有裁定結果的提報（模擬重啟），會在下一筆提報或 `/coc correct list` 時被裁定，而且只裁定一次。
- **`unverified`：** 這類提報不佔用待處理上限，仍可列出、之後的 KP 仍可裁定、提報者仍可撤回；提報者的第 4 筆 `unverified` 只會擋住他自己的下一筆提報。
- **不洩漏劇透：** 如果裁定的證據包含尚未揭露的劇本段落或其他玩家的私人訊息，公開貼出的內容不會出現任何受保護的詞（用 `collect_protected_terms` 驗證）；如果過濾會改動內容，就貼出一般性的替代說明。
- 所有自動測試都 mock 供應商。正式啟用前，另外用一組已標註答案的真實歷史提報，手動跑一次評估。

## 上線順序

要**早於或同時**於移除 `keeper` 身分組上線，讓沒有 KP 助手的群組，永遠都有可行的裁定管道。
