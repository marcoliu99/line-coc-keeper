# 從 Discord 上傳進行頁面級劇本修復

[English](discord_page_level_scenario_repair_design_spec.md)

狀態：**已實作**。這份取代先前的多階段設計（新的不可變劇本庫版本、私訊數值報告、衍生產物世代）：那個設計遠大於需求，而且新的劇本庫版本還會讓英文劇本的匯入再跑一次。

## 1. 問題

PDF 劇本解析一次後，有幾頁解析錯誤；載入訊息會列出需要核對的頁。Keeper 手上有那幾頁正確的文字，是用 ChatGPT、Gemini 或其他工具從原始 PDF 重新擷取的，想直接放進去，不要重新匯入劇本。

## 2. 行為

上傳 `repair_<名稱>.md`。它的行為和 `role_*.md` 角色卡一樣：屬於對話的檔案、覆蓋融合進現有內容、持久，重傳就是再覆蓋一次。

- **格式。** 檔案使用劇本文字本身的頁碼標記：`--- 第 N 頁 ---` 後面接實體第 N 頁完整的修正後文字，頁數不限、順序不拘。第一個標記之前的文字會被忽略，整份答案外面包著程式碼區塊也可以。劇本沒有的頁碼、重複的頁碼、空白的頁面都會讓整份檔案被拒絕。範本是 `docs/references/scenario_page_repair_template(.md|_zh.md)`。
- **融合。** 只替換列出的頁面。劇本文字的其他每個位元組（包含未改動頁面自己的空白）都原樣保留：所有位移都取自原文，結果一次建好。
- **套用範圍。** 對話已載入的劇本：`GroupState.scenario_text` 與儲存的頁面在同一個狀態交易裡一起替換。角色、進度、房間、時間線與劇本庫條目都不動，也不重新匯入或重新翻譯。
- **持久。** 儲存的頁面（`app/repositories/page_repairs.py`，和手動預製角色資產一樣以對話與劇本為鍵）會在每次安裝劇本時（`scenario_activation.install_context_fields`）蓋回劇本庫文字上，所以 `/coc scenario use` 也保留它們。它們綁定條目的來源雜湊，劇本庫條目本身改變（重新解析或重新上傳 PDF）時就會被忽略；綁定舊文字的翻譯版維持原樣。
- **回覆。** 被替換的頁碼；或這些頁面已與目前文字相同；或檔案沒有套用的原因（沒有載入劇本、檔案讀不懂、劇本沒有那一頁）。回覆絕不重複頁面文字。
- **誰能用。** 對話中任何人，和 `role_*.md` 上傳一樣。戰鬥進行中會拒絕變更（`resource_bridge.guard_replacement`），和角色卡上傳一樣。
- **路由。** `repair_*.md` 在一般 Markdown 比對之前就被分流，絕不進入它；一則訊息只能附一份。

## 3. 不做

新的劇本庫版本、數值變動報告、PDF 與標題的綁定檢查、世系與冪等的記帳，以及重建 NPC／地點索引、預製角色或翻譯。修錯了就重新上傳該頁。

## 4. 測試

`tests/test_scenario_page_repair.py`：解析（標記、前言、程式碼區塊、BOM 與 CRLF、被拒絕的檔案）、融合保留未動頁面的位元組且只替換列出的頁面、上傳只改變進行中遊戲的文字、重複上傳不變、失敗回覆，以及修復在從劇本庫重新載入後仍在、而且只對這場對話。`tests/test_upload_routing.py`：路由與一份檔案的規則。
