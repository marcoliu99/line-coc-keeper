# 劇本生命週期深模組

類別：`refactor`。狀態：**已於重構分支實作**。基線：2026-10-05 fetch 後的 `origin/main_v2`，commit `9478dc2`。本規格記錄修改前觀察到的行為；實作與驗證另記於 `docs/architecture/scenario-lifecycle-refactor.md`。Discord 文案、儲存格式、OCR 規則、Markdown 解析規則及戰鬥規則均不預期改變。

## 問題與目標

劇本提交、待選、重新解析、切換與啟用橫跨 `scenario_ingestion.py`、`system.py`、`uploads.py`、`scenario_activation.py`、劇本庫與狀態交易。`system.py` 仍需了解待選字典、清除時機、時間線重置、調查員角色卡安裝、提交與圖片發布順序。PDF 與 Markdown 也重複相同的生命週期。目標是一個深**模組**：小**介面**表達呼叫端意圖，順序與政策留在**實作**。**接縫**位於命令／上傳呼叫端與劇本生命週期之間，來源解析先產生可發佈的劇本候選。呼叫端取得**槓桿效益**，規則修改集中、具有**局部性**。

### 目前外漏至呼叫端的知識

`system.py` 知道相似劇本待選字典與暫存 key、重新解析領取／恢復的交易順序、切換劇本的時間線與檢定重置、有效地圖位置保存、預製角色擷取／安裝、先提交後發布圖片，以及模板與預熱順序。`uploads.py` 知道處理待選時必須持鎖，也自行寫入多份 PDF 暫存狀態。PDF 和 Markdown 匯入各自知道如何建立同一種待選與首次啟用。這些是生命週期實作知識，不是命令解析知識。

## 範圍與非目標

範圍包括 PDF／Markdown 提交、相似劇本與新舊選擇、重新解析領取／恢復／取消、選用既有劇本、合併 PDF 提交成功後消耗暫存來源、首次啟用、調查員與預製角色整合、時間線與待處理狀態重置、權威提交與圖片順序。來源解析器與儲存維持內部協作者。

不包括戰鬥、Keeper 敘事、provider 實作、OCR／版面、Markdown 解析語義、章節推進工具、地圖上傳、角色卡上傳、來源審查／編輯、`/coc newgame`、劇本庫刪除及無關命令整理。驗證身分留在命令／上傳入口；生命週期模組於重讀最新狀態後重新確認依狀態而定的准入條件。不預計變更儲存 schema 或遷移資料。

## 建議的介面與接縫

依現有 Python 慣例，優先用少量模組層入口，而非只為間接呼叫建立 class。呼叫端應能表達四種意圖：提交來源或已準備的候選、處理待選的新舊選擇、重新解析或取消相似 PDF、啟用既有庫劇本。實際 Python 名稱及簡單結果型別待特徵測試後確認。

介面回傳必要的結果與文案中繼資料；命令 handler 負責呈現文字，並保留長時間解析前立即回覆的時機。介面不外露 `GroupState`、待選字典、`sqlite3.Connection`、呼叫端持鎖要求或「準備 → 呼叫端提交 → 啟用」順序。呼叫端可依檔名辨識 PDF／Markdown；解碼、抽取與劇本庫發佈留在內部來源 adapter。兩種真實來源格式足以支持此內部接縫。SQLite／檔案庫可用本機暫存資料庫與目錄測試，無須額外造遠端 port。

模組實作可由來源 adapter、協調邏輯、狀態轉換及呈現中繼資料組成；外部介面仍要小。不可把 Discord 文案、PDF OCR、Markdown parser 或資料庫實作全部塞進一個巨大模組。

## 必須保留的轉換順序

1. 讀取狀態供早期拒絕；驗證來源，於會話鎖外執行耗時的預覽／解析。
2. 以現有格式發佈劇本庫來源。PDF 相似時改為暫存位元組並持久化待選，不做完整解析。
3. 取得會話鎖，重新讀取最新狀態，再查版本、待選、時間線及依狀態決定的准入；不以舊快照蓋掉並行回合。
4. 待選只提交待選引用與中繼資料。啟用則依目前政策轉換最新狀態，在同一 SQLite 交易中擷取並安裝手動預製角色卡，提交一次。
5. 成功提交後才刷新衍生頁圖。圖片失敗只回報警示，不回滾已提交劇本。模板通知與預熱維持既有時機。
6. 釋放會話鎖後再送最終回覆。重新解析必須持鎖領取與提交暫存項、釋放鎖做解析，再依目前條件丟棄或恢復。

使用既有 `state_transaction` 契約。若無法證明外顯行為與競態語義相同，保留嚴格快照提交路徑，但將其所有權收進生命週期模組。

## 特徵測試與驗證計畫

先透過現有命令／上傳入口，使用暫存 SQLite 與劇本庫，觀察持久化結果；新增模組後再透過它的介面測試。涵蓋 PDF 首次提交、相似暫存、新舊選擇、圖片不得提前發布；Markdown 首次提交與待選、純文字來源格式及相同生命週期狀態；選用／切換既有劇本的時間線、歷史、調查員、待處理檢定／Luck、檢定紀錄、地圖位置、劇本中繼資料、圖片、手動角色卡；重新解析成功、驗證失敗、抽取例外／取消、並行寫入及不復活舊待選；提交失敗與圖片失敗的不同結果；兩份並行提交或解析期間到來的待選；既有訊息、按鈕與錯誤文字。

執行相關測試及可行的完整測試套件，並跑既有 `ruff check .`、`mypy app`、CI 靜態檢查；檢查完整 diff、依賴方向及 `git diff --check`。新測試不應大量 patch 私有生命週期函式。

## 依賴方向與完成標準

目標方向：命令／上傳呼叫端 → 劇本生命週期模組 → 來源 adapter、劇本庫、狀態交易、狀態／領域及圖片刷新。生命週期模組不匯入 Discord command handlers；儲存及來源 parser 不指揮啟用。成功標準是修改一條生命週期規則時，主要只需修改單一模組，而不必同時改 upload/system handler、待選機制、啟用順序與交易流程。

實作後撰寫 `docs/architecture/scenario-lifecycle-refactor.md`，記錄前後架構、介面、順序、保留的不變條件、風險，並**只分析** Game Opening 與 Combat Obligations 兩候選；此 PR 不實作它們。

## 取捨與待檢視問題

- PDF 與 Markdown 的拒絕／待選文案目前不同；共用生命週期政策時仍須保留原字句，不因來源型別建立第二套生命週期。
- `scenario use` 與全新上傳的重置集合不同，且切換時保留有效地圖位置；本次先以測試釘住差異。日後若要修正語義，另補失敗中的回歸測試並明記前後差異。
- 檔案系統劇本庫發佈與 SQLite 提交並非單一原子交易。保留先發佈後提交，後續失敗可能留下未引用項目，列為既有風險。
- 多份 PDF 暫存屬來源準備，但成功合併後的消耗目前由 handler 修改狀態。實作時決定是納入生命週期提交，或由狹窄的內部協作者處理；handler 不應再排序清理交易。
