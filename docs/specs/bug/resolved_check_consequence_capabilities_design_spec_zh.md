# 已結算檢定的安全後果

[English](resolved_check_consequence_capabilities_design_spec.md) | [文件索引](../../README_zh.md)

## 狀態與範圍

分類：`bug`。狀態：**implemented（已實作）**。基準為 `main_v2` 的 `7cef87c`。

本規格處理調查員檢定結算後才發生的後果。它對應兩個實際失敗：非戰鬥傷害骰已擲出，但受限的檢定後續無法把傷害提交至 HP；Spot Hidden 成功後需要建立新的 Dodge 檢定，後續流程卻只能問玩家打算怎麼做。

## 目標

保持原檢定不可變，同時允許其已驗證結果產生新的、範圍受限且已授權的後果：非戰鬥傷害或另一個獨立的玩家檢定。

## 必要行為

1. 將 `apply_resolved_check_damage` 加入已結算檢定的後續能力。輸入包含調查員、`damage_expression` 與 `final_damage` 二選一、型別化的 `damage_type`、`source_check_id`、`source_event_id`、`consequence_key` 及人類可讀的 `cause`。
   - 若輸入骰式，由 deterministic dice engine 擲一次；骰值收據、HP 變更與後果收據必須原子提交。
   - 若輸入已結算傷害值，只套用該數值，不得再擲骰。
   - 保留既有重傷規則；必要時在同一次狀態變更中登記 CON 檢定。
   - 不得因此開放通用的 `adjust_character`。

2. 新增 `create_triggered_check`（或具相同限制的工具），用於建立由已結算檢定觸發的新檢定。輸入包含調查員、技能、難度、來源檢定／事件 ID、型別化觸發條件、後果鍵與行動情境。工具建立新的待處理檢定及新的 `check_id`；不得代替玩家擲骰。
   - 原檢定維持已結算，不得重建或重擲。
   - 新檢定使用既有檢定生命週期所有權閘門，並由玩家透過原有按鈕或指令擲骰。
   - 即使群組開啟 autoroll，這種觸發檢定仍須由玩家擲骰。

3. 兩個工具都必須驗證目前時間線、來源檢定／事件、行動者與目標角色身分、已結算結果，以及該型別後果是否獲准用於此結果。`cause` 或 `trigger_condition` 等呼叫端文字只供描述，不能單獨作為授權。

4. 後果唯一鍵為 `(timeline_id, source_event_id, consequence_key, subject_id)`。持久保存包含傷害結果或新待處理 `check_id` 的收據。相同呼叫重試時回傳原收據，不得重擲、重扣 HP 或再建一個檢定。同一鍵若搭配不同參數，必須拒絕。

5. 後果收據與授權必須獨立於有筆數上限的 `resolved_check_events` 顯示／稽核清單持久保存。過期時間線、行動者或目標不符、授權不存在或結果不符時，必須拒絕且不變更狀態。更換時間線時，舊授權及待處理後果失效。

6. 更新檢定後續敘事政策：不得重建、重擲或重新解讀來源檢定。若授權後果是新檢定，必須呼叫 `create_triggered_check` 並交由玩家擲骰；若授權後果是傷害，必須透過 `apply_resolved_check_damage` 提交，不能只在敘事中描述扣血。

## 流程

```text
檢定 A 結算
  -> 驗證持久保存且綁定結果的後果授權
  -> apply_resolved_check_damage -> 收據與 HP／CON 狀態
     或
  -> create_triggered_check -> 新待處理檢定 B
  -> 以相同後果識別重試時回傳既有收據
```

## 非目標

- 不把通用 `adjust_character` 或 `skill_check` 加入已結算檢定白名單。
- 不新增固定 LLM 審稿階段，也不重跑原檢定。
- 不依敘事合理性推測傷害骰式或檢定觸發條件；必須有劇本規則與依據授權。
- 不改變一般檢定、一般戰鬥傷害工具、隱私投影或 KP 助手權限。

## 資料與整合要求

- 來源 `skill_check` 可在擲骰前攜帶有筆數上限的 `consequences` 計畫；每項包含穩定鍵、結果條件、型別、劇本原文引句及傷害或下一檢定參數。Python 對照目前劇本文字檢查引句，並核對傷害骰式確實出現在引句中。計畫經待處理檢定、Luck 決定與結算結果傳遞，在 Narrator 後續開始前持久保存。後來填入的 `cause`、`trigger_condition` 不會產生新授權。
- `final_damage` 只能採用來源檢定預先授權的同一固定值；若傷害先在別處擲出，卻沒有持久保存且可連結的收據，不得把該骰值當作已授權的固定傷害。
- 持久保存與結果綁定的後果授權，以及以時間線、來源事件、後果鍵和目標為索引的冪等收據。有筆數上限的 `resolved_check_events` 不足以作為重試帳本。
- 工具呼叫必須綁定可信請求脈絡中的原始行動者，不得信任模型提供的 actor ID。目標必須由來源事件中的角色身分解析，不能只比對顯示名稱。
- 骰值產生、HP 變更、重傷處理、收據持久化與後續檢定登記，必須經由既有權威狀態變更／檢定生命週期邊界處理。部分提交不得留下「骰值已消耗但 HP 未更新」的狀態。
- 除非另有明確授權，這兩個工具不得供一般不受限呼叫使用。

## 驗證計畫

- 已結算的非戰鬥傷害骰式只擲一次、HP 只變更一次；重複呼叫或 provider 重試均回傳相同收據。
- 已結算傷害值不再擲骰；錯誤時間線、行動者、目標、結果、傷害型別或後果鍵不能變更狀態。
- 重傷傷害沿用既有 CON 檢定閘門，且不建立重複待處理檢定。
- Spot Hidden 成功的授權可建立不同的 Dodge 待處理檢定；重複同一後果回傳相同 `check_id`，嘗試重建來源 Spot Hidden 檢定則遭拒。
- 開啟 autoroll 時，觸發檢定仍由玩家擲骰；原檢定結果保持不變。
- 以來源案例測試床襲擊的觸發及傷害。原始《The Haunting》PDF 的實體第 9 頁（印刷第 25 頁）確認墜落傷害為 `1D6 + 2` HP，Spot Hidden 成功可嘗試 Dodge。解析後的劇本文字也包含這個骰式，但雙欄擷取將其與 Bed Attack 標題拆開，檢索仍可能漏掉關聯。本次驗證引文依據，未修復 PDF 欄位順序。
- 先跑工具閘門、檢定生命週期、狀態持久化與 Narrator 交接的聚焦測試，再跑完整測試、Ruff 0.16.8、mypy 與 compileall。

## 實作決定

來源 `skill_check` 在擲骰前驗證並攜帶後果計畫。人工擲骰、Luck 與 autoroll 都保留此計畫；結算事件在 Narrator 後續前發布持久來源。兩個後果工具均核對此來源與實際結果。自由文字 `cause` 或 `trigger_condition` 不能自行授權後果。
