# Handing an item to another investigator is one committed step

[繁體中文](inventory_transfer_design_spec_zh.md)

Status: **backlog** (design only; no code in this change). Base: `main_v2` at `0de529b`.

## Problem

Two real five-player runs on `1fd3ccb` show items disappearing in a hand-off, and the player is told something generic.

Dead Boarder, 200 turns, `NARRATION_OUTSIDE_MUTATION_LOCK=true` (`turns.jsonl`, `turn.fallback` events and `api-events.jsonl`):

| Turn | What was committed | How the turn ended |
|---:|---|---|
| 47 | `remove_carried_item` only (D's old book removed; the receiver B never got it) | `executor_no_action`, generic reply |
| 50 | `search_scenario`, `remove_carried_item` | `executor_no_action` |
| 56 | `add_carried_item`, `search_scenario` | `llm.turn.failed`, `TimeoutError` after 120 s with 2 tool calls |
| 94 | `search_scenario` ×2, `remove_carried_item`, `add_carried_item` (four tools) | `executor_no_action` |
| 140 | `remove_carried_item`, `add_carried_item`, `search_scenario` ×2 (four tools) | `llm.turn.failed`, `TimeoutError` after 120 s with 4 tool calls |
| 199 | `remove_carried_item` only (A's forged receipt removed, D never got it) | `unsupported_action` |

The run report counts this as DB200-F3 (a likely issue, "root cause unconfirmed"). Reading the code confirms a cause that does not depend on the model being careful.

## Why it happens (read from the code)

- **A hand-off is two independent commits.** `remove_carried_item` and `add_carried_item` (`app/keeper_tools/inventory.py`) each run their own `mutate_tool_state` and persist at once. Nothing makes the second follow the first. If the turn stops in between (a model that does not finish, a Codex timeout, `CodexError`, the tool budget), the item has left one character and arrived at none.
- **A committed mutation outlives its turn on purpose.** `codex_provider` does not cancel a worker-thread mutation on timeout ("Do not cancel a committed/worker-thread mutation on LLM timeout"), and the player is told "已提交的變更會保留". That is right, but it makes a half-done hand-off permanent.
- **The turn deadline covers the whole Executor run.** `CODEX_TIMEOUT` (120 s) is set once per `run_conversation` (`request_owner.deadline()`), not per model decision. Turns 56, 133 and 140 timed out at 120.017 s after two to four tool calls, so a compound action with several tool rounds can spend the whole budget before it finishes the second half of a hand-off.
- **A hand-off costs two of the four tools a turn may use** (`MAX_TOOLS_PER_TURN=4`). Turns 81, 94, 140, 145 and 148 used exactly four tools and ended incomplete or failed.
- **A hand-off is recorded as a consumption.** `remove_carried_item` appends to `consumed_or_removed_items`, which the Narrator receives as `historical_removals`. An item that was given to a teammate is therefore described to the model as used up or lost.
- **The check that the hand-off was whole happens afterwards.** `turn_resolution._mutation_evidence` recognises a matched remove-then-add pair after both are committed and otherwise returns "incomplete". It cannot undo the first half.
- **Nothing limits whose inventory a tool changes.** Both handlers take any `investigator` and resolve it with `find_character`, which falls back to a substring match. A tool call from player A's turn can edit player B's character, and a near-match name can pick the wrong one.
- **Nothing keeps a hand-off whole.** Items are plain strings with no identity, so nothing relates the entry that left one list to the entry that should arrive in another; a hand-off can leave the item with both or neither.

## Rules

1. **One step.** A hand-off between investigators is a single tool call, `transfer_item(from, to, item, quantity?, source_event_id?)`, that validates everything first and then changes both inventories in one `mutate_tool_state`. It either happens entirely or not at all. The action id is **not a tool argument**: a model that re-sends a call after a lost receipt could invent a different one. Turn-owned code **allocates** a logical operation id for each distinct operation (`<turn id>:transfer:<n>`, a per-turn counter in `tool_gateway`), independent of any argument text. To tell a re-emission from a new operation the gateway keeps a per-turn *fingerprint* of the validated arguments with both endpoints resolved to canonical character ids, plus the item and `quantity`; a call whose fingerprint is already registered reuses that operation's id, so a call naming a character by id and one naming it by name are the same operation. Neither the provider's tool-call id nor the call's position is used, because a re-emitted call gets a new call id and a later position. It passes the id beside `actor_id` through `tool_gateway` to the state transaction ledger (`run_snapshot`'s `action_id`). A re-emitted call with the same turn and the same logical operation, whatever its call id or wording, then returns the original receipt instead of a refusal such as "item not held". `quantity` (default 1; the handler refuses anything that is not an integer of at least 1 before it mutates, because the gateway passes model-produced input to handlers without schema validation) moves that many same-named entries in the one atomic step and is part of the logical operation, so a giver holding two copies who gives both asks for `quantity` 2 in a single call. Within one turn a second identical call (same `from`, `to`, `item`, `quantity`) is a replay by definition and gets the original receipt, which states how many entries moved and how many the giver still holds; `quantity` is the number moved by that call, never a cumulative target, so the Executor is told to batch every copy the player means to give into the first call. A call with a different `quantity` has a different fingerprint and is a new operation that moves exactly that many further entries, or is refused when the giver does not hold that many. **Where replay applies:** the Codex provider has a deliberate pre-gateway guard (`codex_provider.py`) that raises `codex_duplicate_tool_attempt` for a byte-identical `(name, arguments)` call in the same turn, because a same-state retry after a tool exception is unsafe; this change leaves that guard alone. Under Codex a verbatim re-emission therefore ends the turn as a fallback whose text names the committed transfer from `observed_outcomes` (rule 6), and the ledger replay covers the calls that do reach the gateway: a re-emission whose arguments differ in form but not in meaning (a character named by id the first time and by name the second) and every call from providers whose adapters correlate each emission with a fresh call id. The same applies to the batched `remove_carried_item` of rule 4: under Codex a verbatim re-emission raises `codex_duplicate_tool_attempt` and the turn ends as a fallback that names the committed removal from `observed_outcomes` (so `observe_tool` projects `remove_carried_item` receipts with the operation id as well), and the ledger replay covers the equivalent-but-differently-spelled and fresh-call-id cases. `source_event_id` stays optional record metadata.
2. **Validate before mutate.** The transfer is refused, with a reason the Keeper can use, and nothing is written, when: the giver is not the acting player's character (unless the speaker is the KP Assistant); the receiver is unknown, not active, or the same character; the item is not in the giver's list by exact normalised match (no substring fallback). **Both endpoints are resolved without fuzzy matching**: `from` and `to` must be a canonical character id or an unambiguous exact normalised name; the substring fallback of `support.find_character` is not used for a transfer, and an ambiguous or partial name is refused with the candidates named.
3. **Only your own character, except by transfer.** `add_carried_item` and `remove_carried_item` act only on the acting player's character (`ToolCall.actor_id` is the field for it, but it is **not populated today**: ordinary inventory calls take the `else` branch in `tool_gateway` (`app/agents/tool_gateway.py`) that calls `execute_tool` without `actor_id`, and both correction paths build `ToolCall` with its empty default). Propagating `actor_id` through the gateway and through both correction call sites is therefore the **first step** of the implementation and lands before the gate; enforcing the gate without it would reject every ordinary add/remove. Another investigator's inventory changes only through `transfer_item`, or when the speaker is the KP Assistant. The correction paths (`correction_adjudication`, `natural_corrections`) keep working because, once they pass the claimant's id as `actor_id`, they act on the claimant's own character.
4. **A remove says why.** `remove_carried_item` takes a `quantity` (default 1, validated like the transfer's: an integer of at least 1) that removes that many same-named entries in one atomic step, with a turn-allocated operation id and argument fingerprint exactly as in rule 1 so a re-emitted removal replays the stored receipt instead of deleting a further copy, and a `reason` of `consumed`, `lost`, `dropped` or `destroyed`. `given`/`handed over` is refused with a pointer to `transfer_item`, so a bare removal can no longer stand in for a hand-off. The reason is chosen by the model, so it is not the only guard: rule 7 adds a server-owned check that refuses a removal of an item the player's own message is handing to someone, whatever reason the model gave. `consumed_or_removed_items` keeps the reason; a transfer writes a separate `inventory_transfers` record (id, turn, from, to, item, quantity, source_event_id) and not a consumption.
5. **A transfer conserves the item; it does not decide uniqueness.** `transfer_item` moves exactly `quantity` list entries from the giver to the receiver, so the number of entries across investigators is unchanged. Duplicate acquisitions stay legal (two investigators may each find a flashlight). Treating an item as a single artifact needs per-item identity or provenance, which the string lists do not have; see "Not done".
6. **The reply matches the state.** When a turn ends in a fallback, the guidance names what was committed, taken from the tool events and not from model text ("已提交：D 把〈古書〉交給 B"), so a half-finished turn no longer reads as nothing happened. This extends `turn_fallback.guidance`.

7. **A server-owned intent check runs before the first tool.** Turn code, not the model, classifies the player's message with a conservative deterministic detector (a give/hand-over verb, an item the speaker holds, and another investigator's name, in the style of the other turn-intent detectors) and records the result on the turn as a **list of per-item intents**, each one a *hand-off* (item, quantity, receiver), an *incoming hand-off* (item, quantity, giver: another investigator gives the acting player something), a typed *removal* (item, quantity, kind: consume, lose, drop or destroy) or a *multi-recipient grant* (item, recipients), where `quantity` defaults to 1 and is how many same-named entries the message allots to that intent, so a compound message such as "give the book to B and drop the key" yields a hand-off for the book and a drop for the key at once, and each guarantee below is checked against the intents for that item only. When the giver holds several same-named entries, each intent is an allocation of entries rather than a ban on the item: a hand-off of 1 and a drop of 1 of the same item are both admitted as long as the allocations together do not exceed what is held, and a call beyond its intent's quantity is refused. The tool gateway first classifies a call whose operation fingerprint is already registered as a **replay** (rule 1): it returns the stored receipt and consumes no allocation, so an exhausted allocation can never keep a post-commit re-emission from reaching the ledger. Only a call with a new fingerprint is then checked against the list, before any inventory mutation: once a hand-off intent's allocation of an item is used up, `remove_carried_item` of that item beyond the removal intents' allocations is refused with a pointer to `transfer_item` whatever `reason` the model gave; a player-originated `transfer_item` is admitted only when it matches a positively detected hand-off intent for the same item and the same canonical receiver, and otherwise fails closed with a clarifying question, so a mistaken model call cannot move a player's item to another investigator that the message never named (the KP Assistant and correction paths, through the `system_origin` marker, are exempt); while an incoming hand-off intent names an item, a standalone `add_carried_item` of that item to the acting player's own character is refused with an explanation that the giver must hand it over in their own turn (or the KP applies it through the KP Assistant), because rule 2 requires the giver to be the acting player, so the add would only duplicate the item and recreate the add-without-remove failure of turn 56; while a multi-recipient grant intent names an item, every `add_carried_item` of that item in the turn is refused before the first one runs, so the grant is not half-applied (including to the acting player's own character). The intent check decides in **both** directions and fails closed. A standalone `remove_carried_item` is admitted only when the check has positively classified the message as a removal intent for that item (consume, lose, drop or destroy, with no other investigator as the object). The detector also classifies the *kind* of removal, and the recorded `reason` is that detected kind: a model-chosen `reason` that differs (for example `destroyed` for something the player dropped) is refused with the detected kind named, so the durable removal history cannot say an item was destroyed when it was only dropped; when it cannot tell, the removal is refused and the Executor is told to ask the player what they meant, so an untrusted, model-chosen `reason` can never be the only thing that lets a removal through. Removals by the KP Assistant or a correction path are system-owned and exempt, **but only through a server-owned admission marker**: turn code sets a `system_origin` on the `ToolCall` (the correction paths and the KP Assistant each set their own value) and `tool_gateway` propagates it beside `actor_id`. The public `source_event_id` argument and any model-supplied field are never trusted for this. There is no exemption for scenario events: `event_obligations` and `obligation_gate` do not handle inventory removals today, so a scenario consequence that removes an item arrives as an ordinary model tool call and is subject to the intent check like any other removal (see "Not done"). A phrasing the detector misses therefore costs one clarifying question, not a lost item. The guarantee for party-wide grants arrives with the batch grant (see "Not done").

## Changes (for the implementation)

- New handler `inventory.transfer_item` and tool schema in `keeper_tools/registry.py`. `ToolSpec.kp_assistant` defaults to `False`, `tools_for_speaker_role` omits tools without it and `tool_dispatch.execute_tool` rejects them, so the KP Assistant exemptions in rules 2, 3 and 7 only work if the registry marks `transfer_item`, `add_carried_item` and `remove_carried_item` `kp_assistant=True` and also `kp_canonical_game=True` (without it `kp_tool_result_creates_canon` is false for a call without a leading `!`, and `commit_kp_ooc_turn_result` would record the response as non-authoritative OOC discussion and leave the tool receipt out of canonical history although inventory changed); the change does both and tests that a KP Assistant call, with and without a leading `!`, is admitted and recorded as canon, and a player call that tries to use the KP-only exemption (a forged or missing `system_origin`) is refused the exemption while a player's matching own-character or intent-matched call is admitted normally; descriptions of `add_carried_item`/`remove_carried_item` say when not to use them for a hand-off.
- Closed value sets (`CODING_STANDARDS.md`: closed value sets are types): `app/domain/models.py` defines `SystemOrigin = Literal["kp_assistant", "correction"]`, `InventoryIntentKind = Literal["handoff", "incoming", "removal", "grant"]` and `RemovalKind = Literal["consume", "lose", "drop", "destroy"]` (the `reason` argument of `remove_carried_item` is validated against `RemovalKind`'s past-tense spellings through one mapping), and `ToolCall.system_origin` and the intent records use them, so a misspelt value fails type checking instead of silently losing the trusted exemption or bypassing the reason comparison. The admission check compares `system_origin` against these members, never by truthiness.
- Turn hand-off contract: the intent list is a `TurnPayload` key `inventory_intents` declared in `app/domain/models.py` first, written only by `context_builder` (the stage that fills the pre-model facts) and read by `tool_gateway`; `tests/test_turn_payload_contract.py` gets the key and its owning writer, and fails if another module writes it.
- `tool_gateway` and the two correction call sites: pass `actor_id` and the `system_origin` admission marker into inventory calls (first step, before any gate); `tool_gateway` also derives the turn-owned action id and passes it to the ledger.
- `inventory.py`: own-character check from `ToolCall.actor_id`; exact item match; `reason` on removal; the transfer record on state (`inventory_transfers`). `GroupState` has no such field today and `GroupState.to_dict()`/`from_dict()` enumerate persisted fields (`app/models.py`), so the field and its serialisation and deserialisation are added there, defaulting to empty for old saves.
- `turn_resolution._mutation_evidence`: a successful `transfer_item` event is one verified transfer; the remove-then-add pair matching stays during migration and is removed once the prompt no longer produces pairs.
- Prompt text that tells the Executor to call add/remove for hand-offs (`turn_context.py`, `prompt_builder.py` "Equipment Consistency") says to call `transfer_item` for a hand-off.
- Observability: an `inventory.transfer` event (committed) and an `inventory.transfer.refused` event with the reason; `scripts/summarize_turn_log.py` counts refusals.
- Replay: `mutate_tool_state` returns only `outcome.value`, which is `None` for a duplicate (`state_transaction._replay` puts the persisted data in `TxResult.result`). The transfer stores its receipt with `ctx.set_result` and the duplicate path returns that stored result, either by handling duplicates through `commit_for_snapshot` or by extending the adapter to return `TxResult.result`.
- Receipt projection: `turn_delivery.observe_tool` (which records every invocation, including an idempotent replay) projects `transfer_item` (today only `add_carried_item` and `remove_carried_item`) into `MechanicResult.observed_outcomes`, and the executor result keeps it, so `turn_fallback.guidance` and `prompt_config`'s committed-detail insertion can name a transfer that moved before the turn failed. The projection carries the logical operation id, and outcomes are deduplicated by that id before the fallback text is built, so a replayed call does not report the same committed transfer twice.
- Tool budget: a hand-off uses one of the four tools instead of two.
- Turn intent detector and gateway admission (rule 7), with a `inventory.admission.refused` event naming the intent.

## Verification the implementation must include

- Each observed case is a regression fixture: turn 47 and 199 (a removal with no receiver must be impossible), 56 (an add with no matching remove), 140 (a four-tool turn that times out after the hand-off: the item is with the receiver and the reply says so).
- Atomicity: a failure injected between the two inventory writes leaves both inventories unchanged.
- Refusals: wrong giver, unknown receiver, receiver equals giver, item not held, substring-only item match, substring-only or ambiguous name for the giver or the receiver (a partial name of another active investigator must not receive the item); each writes nothing.
- Copies: a giver holding two same-named entries who gives both with `quantity` 2 ends with none and the receiver with two, in one commit; a second identical single-copy call in the same turn returns the first receipt and moves nothing.
- Codex duplicate guard, removal: under the Codex provider a verbatim re-emitted `remove_carried_item` also raises `codex_duplicate_tool_attempt`, and the resulting fallback names the committed removal once.
- Codex duplicate guard: under the Codex provider a verbatim re-emitted `transfer_item` still raises `codex_duplicate_tool_attempt`, and the resulting fallback names the committed transfer once; a differently-spelled but equivalent call reaches the gateway and replays the stored receipt.
- Replay content: a re-emitted call returns the stored receipt (not `None`) after the first attempt committed, including after a simulated lost response.
- Conservation: after a transfer the number of entries across investigators is unchanged, and a duplicate item the receiver already holds stays a second entry.
- Idempotency: the same call re-emitted in the same turn with a new provider call id, a later position and different model text returns the original receipt and changes nothing; the model cannot choose the id.
- Incoming hand-off: "B hands me the book" refuses `add_carried_item` of the book for the acting player before any mutation, `transfer_item` from B by the acting player is refused (the giver is not the actor), and the table is told the book moves when B gives it.
- Replay versus allocation: with a one-item hand-off intent, a first `transfer_item` of quantity 1 commits and the same call re-emitted after a simulated lost receipt returns the stored receipt without being refused for exceeding the allocation, and a different further transfer of the item is still refused.
- Removal quantity: "drop both flashlights" is one `remove_carried_item` with `quantity` 2 and `reason=dropped`; the same call re-emitted after a lost receipt returns the stored receipt and removes nothing more, and `quantity` 0 or a non-integer is refused before any mutation.
- Duplicate copies: with two flashlights held, "give one flashlight to B and drop the other" admits one transfer and one `reason=dropped` removal, and refuses a second transfer or a second drop beyond the stated allocations.
- Compound message: "give the book to B and drop the key" admits `transfer_item` for the book and `remove_carried_item` with `reason=dropped` for the key in the same turn, and refuses a drop of the book or a transfer of the key.
- Transfer admission: a `transfer_item` under a message with no hand-off intent, or naming a different item or receiver than the detected one, is refused with a clarifying prompt; a matching one is admitted.
- Reason binding: a player message that drops an item with the model emitting `reason=destroyed` is refused with `dropped` named; the matching reason is accepted and recorded.
- Replay in fallback text: a fallback after a first call and its replay names the transfer once.
- Quantity: An omitted `quantity` is accepted as 1 (the plain three-argument call); `0`, a negative value and a non-integer are refused before any mutation; `source_event_id` survives a save/reload in the record.
- Persistence: `inventory_transfers` survives a save/reload and an old snapshot without the field loads with an empty list.
- Fail-closed removal: a standalone removal under a message the check cannot classify is refused with a clarification prompt, and one under a message classified as a removal intent is admitted.
- Intent admission: a message that hands an item to a named investigator makes `remove_carried_item` of that item refused even with `reason=lost`; a message granting an item to several investigators makes every `add_carried_item` of the turn refused, including the one for the acting player's own character; an unrelated removal in the same turn still works.
- `actor_id` reaches inventory tools through the gateway and the correction paths; an ordinary player's add/remove of their own character still works.
- A removal with `reason=given` is refused; `consumed` is accepted and recorded.
- The correction paths still add to the claimant's character.
- Fallback guidance names a committed transfer and nothing else, and does so when the turn then times out (the transfer appears in `observed_outcomes`).

## Not done

- Scenario-caused removals (a scenario rule that takes an item from a character). A removal with a trusted scenario origin needs inventory-removal extraction and deterministic execution in `event_obligations` / `obligation_gate`, which handle only checks, damage and Sanity today. Until then such a removal under a message the intent check cannot classify is refused and the Executor asks the player, or the KP applies it through the KP Assistant.

- Single-artifact items and where an item is when nobody carries it (left in a room, held by an NPC such as the landlady in turn 199). This needs an identity or provenance record per item, a location per item, and a scenario-side list of which items are props; it is a larger change and should wait for evidence of how often it happens.
- Undoing a half-finished hand-off already in a saved game, and finding items lost by earlier runs.
- Party-wide grants ("everyone receives a copy"). They cannot be repeated ordinary `add_carried_item` calls: rule 3 refuses an add to a teammate, and four tools cannot cover five investigators, so a partial grant would recreate the partial-inventory problem. Until a trusted, system-owned batch grant exists (validate all recipients, then apply to all in one `mutate_tool_state`, with its own turn-derived action id), a player's turn whose message the intent check (rule 7) recognises as such is refused whole before its first mutation; a phrasing the check misses is not guaranteed atomic. That operation needs its own spec.
- Retrying a turn after an Executor timeout; that is a separate decision (a turn that has committed anything is not safe to replay).
