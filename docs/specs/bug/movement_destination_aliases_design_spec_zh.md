# 有來源依據的移動目的地別名

## 問題與目標

2026-09-28 16:05 的日誌顯示：「我去圖書館」被模型填成「中央圖書館」、「我去老屋」被填成「科比特宅邸」，兩次都得到 `movement_destination_mismatch`。當回合其實檢索到 Central Library 與 Corbitt House；驗證器先要求模型目的地逐字出現在玩家移動子句，再要求同一字串出現在來源或地圖，因此在檢查地圖以前就拒絕了簡稱及中英別名。PR #99 建立嚴格抵達驗證，PR #121 放寬 OCR 地圖不完整的路徑限制，但保留這兩道字串檢查。

目標是在玩家明確移動、且同一劇本地點的不同名稱有當回合來源依據時允許抵達，同時繼續拒絕未要求或無依據的移動。不採用無限制的字串相似度：例如「老屋」與「科比特宅邸」沒有可用的字面重疊，不相關地點也可能共用字詞。

## 範圍與決策

- 預設維持現有嚴格模式。加入可選的環境設定 `MOVEMENT_DESTINATION_MATCH_MODE=source_bound`（預設 `strict`），列入 `.env.example`，啟動時拒絕未知值。這是可暫時放寬目的地名稱比對的開關；它不會關閉玩家授權、既有障礙、待處理檢定／Luck 或來源驗證。
- 兩種模式都必須引用當回合玩家自己寫下的移動子句；保留第三方、否定、假設及 OOC 排除規則。
- `strict` 沿用目前目的地與證據的字面檢查及地圖名稱路徑。
- `source_bound` 先嘗試嚴格檢查。場景轉移若失敗，可使用模型提供的 `player_destination`（必須出現在已授權的玩家子句）與 `source_destination`（必須從已登錄的當回合 RAG 段落複製）。該段落也必須被移動證據引用，並完整包含正規化後的來源地名，不能只靠一般詞彙的片段重疊。三個名稱須解析到**同一筆**地點索引：`destination` 是正名或別名、`source_destination` 是另一名稱或別名、`player_destination` 是名稱／別名或不含歧義的簡稱。另一種依據是同一段經核對的雙語來源明確指出三者是同一地點。多筆候選則拒絕。模型可用既有回應解釋跨語別名；Python 核對名稱、來源身分與唯一性，不增加固定 LLM 呼叫。
- 「圖書館」作為「中央圖書館」的清楚簡稱，若完整目的地有來源依據，可接受；跨語情況仍須上述明確來源欄位，不能只用編輯距離。
- 優先使用既有索引的 `aliases`。若沒有可靠索引配對，同一引用來源須明確把玩家名稱、正典目的地及來源地名指向同一地點。單靠模型宣稱等價不足以通過。若英文只有 `Corbitt House`，正典目的地卻是「科比特宅邸」，且索引沒有別名連結，應回傳 `movement_alias_unverified`，要求更明確名稱或有來源的別名，不得默默瞬移。
- 抵達時儲存已解析的正典名稱；診斷事件只記錄有長度限制的玩家名稱、來源名稱及解析依據，不記錄整段原文或提示。
- 名稱不符、來源不支援、別名未核對分別給可操作回覆，不可全部變成「行動尚未完整處理」。

## 不包含

- 不提供關閉 PR #99 全部移動檢查的開關；那會連玩家授權和抵達順序一起繞過。
- 不加每回合翻譯或審稿 LLM 呼叫、模糊編輯距離門檻、全域別名字典或自動重跑 PDF。
- 不更改既有 `/coc scenario use <劇本ID> <版本ID>`；選用已核准中文 RAG 版本目前就能做，與目的地驗證是兩件事。日誌中的 `requested_variant=original` 表示當局未選中文版本。
- 不從檢索段落虛構場景、房間、路線、遭遇或物品。

## 介面與狀態

- `commit_movement` 工具 schema 加上可選的 `player_destination` 與 `source_destination`；舊呼叫維持有效。Python 依玩家原句與當回合已登錄證據驗證，這兩個欄位不成為正典狀態。
- `MOVEMENT_DESTINATION_MATCH_MODE` 為程序層設定，預設 `strict`；改值後須重啟 bot。既有存檔不需遷移。
- `scenario_location_index` 已有 `name` 與 `aliases`，用作有限候選集；沒有玩家當回合明確行動與證據，索引不能單獨授權移動。
- 中文版本仍由每團 `scenario_variant_id` 選擇；它可能改善檢索，但不能單靠切換就證明「老屋」等於「科比特宅邸」。

## 流程

```text
玩家移動子句 -> 核對原句授權
       -> 待檢定／Luck 與明確障礙
       -> 嚴格目的地＋來源檢查
            | 通過 -> 既有地圖／場景抵達驗證
            | 失敗且 strict -> 分類拒絕
            | 失敗且 source_bound
                 -> 玩家名稱確實在已授權子句？
                 -> 來源名稱確實在當回合引用來源？
                 -> 正典／索引／地圖／來源可唯一連結？
                      | 否 -> 分類拒絕，不改狀態
                      | 是 -> 既有地圖／場景抵達驗證
       -> 抵達結算後才允許目的地相關效果
```

## 測試與驗收

- 在真正 `commit_movement` 接口重現兩筆日誌：嚴格模式維持拒絕；來源模式僅在可驗證別名連結存在時成功。加入索引別名或雙語來源夾具，核對最後抵達位置。
- 只有英文來源、沒有可驗證連結時，不能憑空授權中文正典名稱；回傳 `movement_alias_unverified` 且不改狀態。
- 無關 RAG、過期來源 ID、偽造來源名稱、多個候選地點、玩家提問／否定／OOC、第三方移動、待檢定／Luck、鎖門及反應點在兩種模式都仍會擋下。
- 字面上已有來源支持的目的地仍走原流程；mock 整合回合確認不新增固定 LLM 階段。
- 跑移動／Executor 重點測試、設定測試、ruff、mypy 與完整測試；原始隔離重現中有別名連結的案例須轉綠。

## 待確認事項與取捨

- 實作前查看該團 `scenario_location_index` 與已核准中文版本。日誌證實選用 `original`，但未顯示索引是否包含「老屋／科比特宅邸」別名。若索引和雙語段落都無連結，安全解析器只能要求澄清；若要更寬鬆的管理員覆寫，會犧牲劇本忠實度，需另行明確決定。
- 如果索引本身的別名錯誤，來源模式也可能接受錯誤對應；診斷須帶索引紀錄身分，並提供更正途徑。
