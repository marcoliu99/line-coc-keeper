狀態：已實作。基底：main_v2。分支：bug/scenario-retrieval-tokenizer-readiness。

## 問題與證據

2026-09-27 玩家要求拿取預付款、鑰匙並查看地址，26.76 秒後收到未完成訊息，裁決碼為 `invalid_evidence_reference`。紀錄包含三次成功檢索、六次工具嘗試，但沒有保留另外三次工具名稱與原始裁決引用，不能斷言其具體內容。

部署環境缺少 requirements.txt 已宣告的 `tiktoken`。程式以 UTF-8 位元組保守估算，Executor 輸入估計 65,865，超過設定的 32,000 上限，中文檢索預算因此為零。中文必要依據完全未送入模型；英文補查命中但完整性未知，不能直接證明缺少的中文關聯均已補齊。工具閘門在一般記錄流程之前拒絕機制操作，最終被通用未完成訊息掩蓋。

唯讀狀態確認背包／帳本沒有新增鑰匙與預付款，也沒有待處理檢定或 Luck。開場敘事已描述收到物品，卻沒有對應入帳；不可自動重播或直接修改正式存檔。

## 修正範圍

1. 補齊部署環境缺少的 tokenizer，確認編碼可載入，保留保守後備與預算上限。
2. 初始化 tokenizer 失敗時記錄原因類型，不記錄例外內容、提示詞或憑證。
3. 記錄檢索輸入估計、保留量、可用預算與實際計量方式。已知模型若退回位元組，投影資訊也必須如實顯示。
4. 依據／更正閘門擋下的工具仍須留下事實與診斷，不執行底層工具，不放寬既有裁決與狀態驗證。
5. 未完成且確有依據不足的工具拒絕時，明確說明缺少劇本依據，保留部分變更與檢定保護，不要求玩家為系統問題更正宣告。

不改資料結構、不增加固定 LLM 往返、不編造地址、不把任意英文命中視為完整、不修改正式遊戲狀態。

## 流程

    載入編碼 -> 估算輸入與保留量 -> 分配檢索預算
       | 失敗：保守位元組估計並記錄診斷
    中文依據 -> 完整性閘門 -> 執行工具／記錄拒絕
    裁決交接 -> 既有真實狀態驗證 -> 安全且說明原因的回覆

## 驗證

- 缺 tokenizer：保守計量、診斷與投影資訊正確。
- 離線重建事故兩組中文根節點，對照編碼可用與零預算結果。
- 被拒工具不修改狀態，但會留事實與診斷；無關英文命中不能解鎖。
- 相符完整依據能放行真實背包操作與裁決，模型使用測試替身。
- 未完成回覆維持已提交變更、檢定保護，說明依據不足。
- 執行隔離全套測試、lint 與型別檢查，不呼叫付費模型。

## 限制

離線測試能驗證檢索、閘門、入袋與交接，不能保證真實模型下一輪選擇相同工具。命中講義沒有具體門牌，不應補造。現有 bot 已快取 tokenizer 不可用，需由使用者重新啟動。

## 追加：搜尋候選不等於必要關聯

19:15 的四則排隊提示各來自不同請求，屬於排隊積壓。剩餘檢索錯誤是把排名前五的來源單元全部視為同一組必要依據；本次匯入的紀錄是獨立來源單元，沒有依賴邊，因此無關候選也會阻擋原可裁定的行動。另外 `blocked` 回合仍被敘述成已移動且手持鑰匙，下一回合開門未呼叫工具，裁決引用無效；原始引用未記錄，無法斷言引用了什麼。

排名搜尋先納入第一筆紀錄及其完整必要／條件依賴，再加入能完整容納的其他獨立候選。放不下的候選須另外列出 ID／頁碼／名稱，完整性明確限定為「已選紀錄及必要關聯」，不代表玩家行動的所有依據均已找到。不得將明確必要關聯降級為候選；第一組必要依據也放不下時，仍阻擋並保留可行的續取。

預取最多使用 3,000 token（SCENARIO_PROACTIVE_TOKEN_BUDGET），且仍受原本請求預算限制，保留空間供精準補查。不提高 32,000 總上限，也不調低輸出／安全預留。原文查詢不得夾帶中文游標，提示詞須明確說明。

程式直接保護 blocked 敘事，保留部分變更與待檢定提示，不能把阻擋寫成已移動或已取得物品。無效引用只記錄數量及是否有劇本 context，不記錄原始模型內容。部署前用真實匯入紀錄、事故根節點及連續預算離線驗證；單元測試不能視為真實模型成功的證明。

候選分組驗證：1,046 通過、1 略過、33 子測試通過。使用真實匯入的 32 個來源單元搭配事故三組補查根節點，96 組均未出現選定必要關聯不完整或輸出超過預算；最低補查預算為 3,736 token。未呼叫 embedding 或模型 API；這只驗證可取得依據，不代表已證明商店存在或角色持有鑰匙。

## 追加：tokenizer 載入失敗不得鎖死整個 process

補裝宣告的相依套件並重啟已修復部署，但解析程式本身仍然脆弱。`_encoding` 使用 `lru_cache`，一次載入失敗回傳的 `None` 會被保留到 process 結束。BPE 快取是冷的時候載入需要連網——本機實測冷啟動為 3.76 秒——所以啟動瞬間的暫時性故障，或作業系統暫存目錄被清除，都會讓之後每一次估算靜默改用 UTF-8 位元組。中文因此高估約三倍：事故回合實測 19,213 token 對 64,634 位元組，把 6,643 的餘裕變成 −38,778，檢索預算持續為零，直到有人察覺並重啟。

改用明確的快取解析 tokenizer。成功結果保留到 process 結束；失敗只保留到重試期限（ENCODING_RETRY_SECONDS，60 秒），超過期限的下一回合會重新載入並自行恢復，不需重啟。載入在鎖外進行，避免緩慢下載阻塞其他回合；已解析的對應表維持與原本 `maxsize` 相同的上限。`llm.tokenizer.unavailable` 繼續記錄錯誤類型、嘗試次數與重試區間；新增 `llm.tokenizer.recovered`，只在先前確有失敗被清除時發出，避免把第一次成功載入誤報為事故。兩個事件都不記錄提示詞、憑證或例外內容。

這只縮小窗口，並未消除後備路徑：重試期限內的估算仍是位元組，相依套件長期缺失仍會降級。把「位元組後備下預算為零」判定為基礎設施故障而非劇本依據不足，仍是未解項目。

鎖死修正驗證：1,049 通過、33 子測試通過；ruff、mypy、compileall 均通過。新增兩項離線測試，分別涵蓋暫時性失敗在重試期限內不重載、超過期限後恢復，以及已解析的 tokenizer 被快取、不重載也不發出事故事件。未呼叫模型或 embedding API。
