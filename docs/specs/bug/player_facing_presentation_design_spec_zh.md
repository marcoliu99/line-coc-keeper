# 面向玩家的呈現：等級、內部識別碼、隊伍人數

[English](player_facing_presentation_design_spec.md) | [文件索引](../../README_zh.md)

## 狀態與目標

分類：`bug`。狀態：**已實作**。來源：Camp Sunny 五人 500 回合驗證的 CS-001、CS-003、CS-004（Workstream F）。基於 `main_v2` 的 `aa79f22`。

* CS-001：五位調查員被敘述成六位，來源是劇本內建的預設角色卡或文字。
* CS-003：英文的檢定等級原始值（`regular 成功`、`hard`、`fumble`）出現在玩家看到的內容裡。
* CS-004：內部的 `check_id` 出現在 Keeper 的回覆中。

引擎刻意保留英文等級與不透明的識別碼：已存的事件、日誌與第二階段的 golden trace 都依賴它們（`outcome` 就是存成 `hard 成功`）。所以儲存的形式不變，修正放在玩家閱讀之處的呈現層。

## 契約

1. **呈現層**（`app/presentation.py`）。`tier_label`、`difficulty_label`、`outcome_label` 把引擎的值對應成牌桌的語言（`regular 成功` → `一般成功`、難度 `hard` → `困難`、等級夠高但任務要求更高而失敗 → `失敗（擲出困難成功）`）。未知的值原樣通過。
2. **顯示的地方都走它。** 已結算檢定的公開那一行、結算後的 fallback 與結果區塊、給 Narrator 的歷史與待處理 Luck 文字，以及 Narrator 失敗時的訊息，現在顯示本地化的等級與難度，所以模型複述的是中文而不是照抄英文。
3. **最後一道防線。** supervisor 把最終回覆與每則私訊都過一遍 `presentation.player_text`：`等級 成功/失敗` 與帶標籤的 `難度／等級` 值會被對應，`check_id=…`、`decision_id=…` 以及獨立出現的 `check-<hex>`／`decision-<hex>` 連同括號會被移除，所以模型從上下文照抄的值不會被顯示。一般文字裡的 "regular"、"hard" 不受影響。`DEBUG_SHOW_INTERNAL_IDS=true` 可在除錯時保留識別碼；等級原始值則永遠不會顯示。
4. **不把識別碼交給 Narrator。** 單行的工具事實不再包含 `check_id`、`decision_id`、`timeline_id`、`event_id`、`evidence_ref`；結構化內容、日誌與測試仍保留它們。
5. **真實的隊伍人數。** Narrator 的提示說明目前調查員的人數與名單，並禁止說成其他人數；回覆若宣稱更大的隊伍，會在投遞驗證之前被更正。只考慮文字明確連到玩家隊伍的數量（「你們六位調查員」、「隊伍共有六名隊員」、「你們一行十位冒險者」），而且只改動大於真實人數的數字：較小的可能是子團體（「你們兩位調查員留下」），而「敵方有六名探員」、「你們看到有六名探員」指的是別的團體，不會被改。

## 執行方式

`tests/test_presentation.py`：各種等級與失敗形式、帶標籤的值、一般文字不受影響、冪等；各種識別碼形式被移除且句子保留；除錯開關；交給 Narrator 的事實與提示；公開的檢定那一行與 fallback；最終回覆與私訊被清理；隊伍人數更正、子團體與無關數字不受影響；五位調查員永遠不會被敘述成六位；以及 Narrator 提示帶有真實名單。

## 未涵蓋

正規表示式處理的是驗證中看到的形式（`regular 成功`、`難度 hard`、`check_id=…`）。以其他形狀寫出的等級或識別碼、或用特殊方式表達的隊伍人數（例如「半打」）不會被抓到。`/coc luck <等級>` 這個指令文字仍顯示英文選項關鍵字，因為那是指令實際接受的參數。隊伍人數是已綁定的調查員數量；由 Keeper 扮演的 NPC 隊友不計入。
