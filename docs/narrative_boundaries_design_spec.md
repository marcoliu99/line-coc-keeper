# 設計規格草案：劇情敘事邊界

## 文件狀態

討論稿，已依使用者提供的 **Scenario Canon Boundary — CRITICAL** 收斂第一階段方向：劇本世界事實邊界；尚未決定細部負面查證規則，也沒有程式實作。工作分支：`enhancement/narrative-boundaries-spec`，整合目標：`main_v2`。玩家決策權與場景推進先列為相鄰議題，不能稀釋本期的劇本忠實度要求。

## 問題與目標

Keeper 必須能依劇本描寫環境、扮演 NPC、回應玩家行動並維持懸疑，但不能把「敘事上合理」當作新世界事實的授權。**AI Keeper 是劇本的敘述者與裁定者，不是共同創作新劇本內容的人。**第一階段要阻止它因玩家暗示、檢定失敗、恐怖氣氛或故事需要，而憑空生成劇本未支持的地點、敵人、遭遇或線索。

目標是讓玩家每輪看見有反應的場景，同時可追溯重大劇情變化的來源。這份工作聚焦「敘事內容與世界事實的邊界」，不重做骰子、戰鬥或隱私政策。

## 現況與缺口

- `app/services/prompt_config.py` 的 Narrator 指令已要求依劇本與機制結果敘述，禁止隨意發明關鍵線索、NPC、地點或真相。`docs/keeper_skill.md` 也要求一次只推進一個場景片段。
- `app/agents/narrator.py` 沒有工具，收到劇本／記憶脈絡、權威角色狀態及 Executor 的結果後生成回覆。`app/agents/supervisor.py` 隨後依序執行 Guard、劇透字詞掃描及檢定一致性修正，才將回合文字寫入正式歷史。
- `app/agents/rule_validator.py` 的確定性驗證只抓系統外洩字眼與未閉合的 Markdown；`app/spoiler_policy.py` 的公開回覆掃描只對已收集到的敏感字詞做字面比對。這些檢查無法可靠判斷「擅自新增重要 NPC」「替玩家決定下一步」或「尚未達成條件卻跳場景」。
- Executor 的工具可能在 Narrator 輸出前已改動權威狀態。若只在最終文字上設防，無法撤銷已執行的工具副作用。舊版 `app/keeper.py` 單一 Keeper 路徑也會產生公開敘事，不能只涵蓋 Agentic Supervisor。
- 現有劇透防護處理「何時公開秘密」，但「能否宣稱一件新事情已發生」還需要另一份規則；兩者應共用事實來源，不應把所有新描述一律視為劇透。
- `app/services/prompt_config.py` 已有 `EXECUTOR_SCENARIO_RAG_POLICY`，要求先重用本回合提供的 RAG 片段，缺少會影響判定的具體事實才補查。`app/keeper.py` 在 RAG 模式也要求查不到時不能憑典型 COC 劇本印象腦補。這兩段與既有劇情提示詞必須保留；新規則只補強「資料缺漏不等於創作許可」，不能用每回合重查或額外 LLM 審稿換取邊界。

## Scenario Canon Boundary — CRITICAL（本期核心）

### 1. 不創造劇本內容

未由劇本材料支持，也未由 KP 明確建立或先前正式劇情事件確立的地點、房間、區域、NPC、敵人、生物、物品、線索、事件、通道等世界元素，Keeper 不得發明、添加、假定或暗示其存在。**「沒有寫」不等於「AI 可以合理補上」。**感官描寫也不能暗中構成新結構，例如「牆後傳來骨骸碰撞聲」若等於創造地下室或敵人，就不屬於無害氣氛。

### 2. 地點

只有劇本明確描述／展示，或 KP／先前正式事件明確確立的地點才存在。不能因為建築常識或敘事方便生成地下室、閣樓、密道、隱藏房間等。玩家搜尋或試圖進入未成立的地點時，不得順勢產生該地點及其中的物件；若已確認劇本不存在該處，應清楚告知並在實際場景上結算行動。

### 3. 敵人與遭遇

戲劇張力、檢定失敗、玩家的恐懼、懷疑、提問或假設，都不能單獨生成敵人或戰鬥。敵人登場需要劇本當前條件支持，或 KP／先前正式事件已明確確立其存在。不得先由 Executor 加入敵人或開戰，再由 Narrator 替此行動編造理由。

### 4. 玩家假設與事實優先序

玩家說「我去地下室找骷髏」是行動意圖及假設，不是地下室與骷髏已存在的證據。當玩家期待或敘事合理性與劇本既定內容衝突時，以劇本為準。玩家行動成功也只能改變其實際能改變的狀態，不能反向補出未被授權的世界元素。

劇本給出的是世界基準；先前**已正式結算**的事件可改變當前狀態，例如劇本原本鎖住的門被玩家成功打開，後續敘事須依已開門的現況。KP Assistant 可明確改寫或新增設定，但要能辨識那是一條主持指令，不得從一般玩家話語或模型推測中推導出覆寫。這兩種情況都不是 AI 自行創作新劇本。

### 5. 缺少證據時的回覆

「已確認不存在」和「目前檢索片段沒有提到」必須區分。若完整可用劇本／權威地圖已確認無地下室，可直說沒有地下室；若只是一段 RAG 沒命中，不能憑檢索缺口斷言它不存在，也不能創造它。此時描述眼前可確認的場景，保留未知；只有該事實會影響當前判定時，沿用現有 `EXECUTOR_SCENARIO_RAG_POLICY` 補查。負面查證所需的最低證據仍待討論。

### 候選提示詞文字（供審閱，尚未寫入程式）

```text
【劇本正典邊界｜最高優先】
劇本是世界事實的權威來源。你是劇本的敘述者與裁定者，不是新劇本內容的共同作者。
只有劇本明示、KP 明確建立、或先前正式事件確立的世界元素才可當作存在。
不得因氣氛、常識、檢定失敗或玩家的猜測，創造或暗示新的地點、房間、NPC、敵人、
物品、線索、事件或通道。「劇本沒寫」不是自行補足的許可。
玩家說「我去地下室找骷髏」只表示行動與假設，不證明地下室或骷髏存在。
若已查明劇本沒有該地點，清楚告知並只結算實際場景；若只是目前片段沒有提到，
保留未知，不創造內容。需要補查時沿用既有劇本檢索規則，先重用已有的 RAG 內容。
敵人或戰鬥僅能由劇本條件或已成立的正式事件引入；恐懼、提問與失敗骰不會生出敵人。
敘事合理性或玩家期待與劇本衝突時，劇本優先。已正式結算的狀態變化須繼續保持一致。
```

這段是共用約束的候選文字，不取代現有 `EXECUTOR_SCENARIO_RAG_POLICY`、劇情節奏提示詞、Narrator 的機制事實提示或劇透／隱私政策。落地時需量測新增 token 與回合延遲，並確認 legacy Keeper 與 Agentic 路徑各自只注入一次。

## 待確認的邊界範圍

### A. 劇本與既定事實

第一階段採用上面的嚴格劇本事實邊界。原草案允許「普通群眾反應」或無關主線的即興 NPC，與本次提供的 **任何 NPC 都需有來源** 要求衝突，已撤回該預設。可自由發揮的只剩不宣稱新世界元素的表述方式；是否允許劇本外次要人物，須另由 KP 明確授權。

### B. 玩家角色的決策權

Keeper 可描述玩家已宣告行動的可見後果及必要的即時反應，不可替玩家選擇目的地、接受交易、揭露私密動機、承諾下一步或自動完成尚待玩家決定的選項。NPC 可以主動行動，但不得用 NPC 隊友直接解完核心謎題或代玩家決定路線；這與 `docs/references/gameplay_style.md` 的既有角色定位一致。

### C. 場景與時間推進

每次回覆以當前行動及其直接後果為主。在玩家仍能回應的壓力點停下；跨場景、長時間跳躍、核心線索揭露或劇本章節切換須有明確觸發來源。`advance_scenario_chapter` 是 Context 視窗更新工具，不能把呼叫工具本身當作劇情已達成的證據。需討論哪些事件允許 Keeper 主動推進，哪些必須等玩家選擇或 KP 指令。

本期先處理 A。B、C 可用來避免敘事繞過 A，但不在這次規格修訂中擴成獨立功能。

## 候選設計

1. **最小提示詞補強**：在現有 Keeper／Executor／Narrator 提示詞旁加一段共用的 canon boundary，不覆寫現有 RAG 重用、劇情、防劇透與機制提示詞。提示詞需具體區分「玩家假設」與「已存在事實」、禁止憑失敗檢定生成敵人，並給出地下室例子；避免在每個 agent 重複一大段而增加 token 與延遲。
2. **沿用現有檢索路徑**：本回合已有足夠的劇本片段時直接重用；只有缺少會影響當前行動的具體事實才補查。不增加每回合固定 `search_scenario`、額外 LLM 驗證或第二次 Narrator 呼叫。檢索仍無法確認時，不能補造內容。
3. **在狀態變更前設邊界**：若實測顯示提示詞仍會讓 Executor 擅自 `start_combat`、`add_npc_to_combat` 或建立重要事實，評估在對應工具入口檢查來源及當前條件。僅靠 Narrator 事後改字無法處理已落庫的副作用；不能用沒有證據的通用「世界元素偵測器」直接阻擋所有工具。
4. **在敘事輸出前核對**：若仍出現文字憑空創造地點或敵人，評估是否有足夠結構化資訊做低成本檢查；沒有可靠依據時先保留未知或使用中性回覆，不設每回合額外 LLM 審稿。
4. **兼顧兩條路徑**：Agentic Supervisor 與仍在使用的 `keeper.run_turn` 應套用同一政策定義；KP Assistant 的明確主持修正可新增／覆蓋事實，但應保留來源與範圍，不由一般玩家話語冒充。

第一階段優先低成本提示詞補強與真實案例驗證；若無法守住，再依具體失敗點補工具前置檢查或輸出檢查。純關鍵字無法可靠辨識「世界元素是否由劇本授權」，不列為唯一防線。

## 資料結構與相容性

討論稿不新增資料庫欄位。若採事件分類，優先評估沿用 `GroupState.established_facts`、`known_clues`、現有工具結果與正式回合紀錄；是否需要另存事件來源、是否需要標示「推測／已確立／已揭露」，須由具體案例決定。不能把舊劇情文字無條件升格為權威事實，也不能以新規則改寫既有存檔或玩家角色數值。

現有 `docs/keeper_skill.md` 容許玩家帶有未登記但合理的日常小物，亦要求 Keeper 主動用既有 NPC 意圖和環境變化維持張力。嚴格解讀「劇本沒寫的任何物品／事件都不可新增」會收緊這兩項既有玩法；實作前需明確決定是否只禁止具有調查或機制效果的物品與事件，或連普通背景物件也一律要求劇本／KP 來源。不能在未討論下悄悄改掉既有物品政策。

## 非目標

- 不在本分支修改 runtime、提示詞、工具 schema 或資料表。
- 不重設 `SPOILER_PROTECTION_ENABLED`／`PRIVACY_ISOLATION_ENABLED` 的意義。
- 不讓自動審稿器替 KP 決定唯一合法劇情；KP Assistant 仍是主持層的明確覆寫來源。
- 不要求所有日常敘事細節都先記錄為結構化事實。

## 驗證計畫

- 收集至少數個「本來應允許」與「確實越界」的真實回合，標記原始輸入、劇本可用片段、當時狀態、工具呼叫、輸出及期望的停點。優先包括「玩家找不存在的地下室／骷髏」「失敗檢定憑空冒出敵人」「NPC／線索由玩家猜測變成事實」。
- 覆蓋：普通感官描寫、NPC 合理反應、未揭露線索、玩家尚未決定的選項、場景轉換、KP 明確改寫設定，以及沒有劇本可查的自由場次。
- 分別驗證 Agentic 與舊版 Keeper 路徑；若涉及工具前置檢查，確認被拒絕時沒有部分狀態更新；若涉及輸出重寫，確認正式歷史只保存最終送出的文字。
- 比較修訂前後的工具呼叫次數、RAG 查詢次數、模型 iteration、額外 token 與回合延遲；不接受靠每回合多一輪 LLM 呼叫才達到的修正。並記錄越界率與誤擋率，再決定是否需要第二階段防線。

## 討論決策

1. 單次 RAG 未命中時已確定不可創造元素；若要對玩家明說「地下室不存在」，最低需要哪些負面證據（完整劇本、權威地圖、KP 明確否定）？
2. KP Assistant 的主持指令若與劇本衝突，是否可即時覆寫？若可，如何標明這是明確改編而非 AI 自行推翻劇本？
3. 不增加 LLM 往返的前提下，哪幾個真實案例最值得做對照試驗，判定提示詞補強是否足夠？
4. 劇本未列出的普通隨身物品與無機制效果的環境細節，是否也採完全禁止？這會影響現有合理攜帶物政策與敘事流暢度。
