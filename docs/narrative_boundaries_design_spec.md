# 設計規格草案：劇情敘事邊界

## 文件狀態

使用者已確認開始實作第一階段。已採用共用提示詞邊界、專用 `/coc correct` 提報及 KP 裁定流程；具體情境仍須實測。合理的日常隨身小物與不影響劇情／機制的感官細節可保留；單次 RAG 未命中時回覆「目前無法確認」，必要時補查。工作分支：`enhancement/narrative-boundaries-spec`，整合目標：`main_v2`。玩家決策權與場景推進先列為相鄰議題。

## 問題與目標

Keeper 必須能依劇本描寫環境、扮演 NPC、回應玩家行動並維持懸疑，但不能把「敘事上合理」當作新世界事實的授權。**AI Keeper 是劇本的敘述者與裁定者，不是共同創作新劇本內容的人。**第一階段要阻止它因玩家暗示、檢定失敗、恐怖氣氛或故事需要，而憑空生成劇本未支持的地點、敵人、遭遇或線索。

目標是讓玩家每輪看見有反應的場景，同時可追溯重大劇情變化的來源。這份工作聚焦「敘事內容與世界事實的邊界」，不重做骰子、戰鬥或隱私政策。

## 現況與缺口

- `app/services/prompt_config.py` 的 Narrator 指令已要求依劇本與機制結果敘述，禁止隨意發明關鍵線索、NPC、地點或真相。`docs/keeper_skill.md` 也要求一次只推進一個場景片段。
- `app/agents/narrator.py` 沒有工具，收到劇本／記憶脈絡、權威角色狀態及 Executor 的結果後生成回覆。`app/agents/supervisor.py` 隨後依序執行 Guard、劇透字詞掃描及檢定一致性修正，才將回合文字寫入正式歷史。
- `app/agents/rule_validator.py` 的確定性驗證只抓系統外洩字眼與未閉合的 Markdown；`app/spoiler_policy.py` 的公開回覆掃描只對已收集到的敏感字詞做字面比對。這些檢查無法可靠判斷「擅自新增重要 NPC」「替玩家決定下一步」或「尚未達成條件卻跳場景」。
- Executor 的工具可能在 Narrator 輸出前已改動權威狀態。若只在最終文字上設防，無法撤銷已執行的工具副作用。舊版 `app/keeper.py` 單一 Keeper 路徑也會產生公開敘事，不能只涵蓋 Agentic Supervisor。
- `record_established_fact`／`record_clue` 目前檢查非空文字、visibility 與重複內容後便可保存；工具成功只證明「資料寫入成功」，不自動證明輸入內容符合劇本。未來若以這些記錄作正典來源，寫入前也須檢查來源，否則 AI 可先記錄自己編的密門，再引用該記錄繞過邊界。
- 現有劇透防護處理「何時公開秘密」，但「能否宣稱一件新事情已發生」還需要另一份規則；兩者應共用事實來源，不應把所有新描述一律視為劇透。
- `app/services/prompt_config.py` 已有 `EXECUTOR_SCENARIO_RAG_POLICY`，要求先重用本回合提供的 RAG 片段，缺少會影響判定的具體事實才補查。`app/keeper.py` 在 RAG 模式也要求查不到時不能憑典型 COC 劇本印象腦補。這兩段與既有劇情提示詞必須保留；新規則只補強「資料缺漏不等於創作許可」，不在每個回合固定增加一次 RAG 搜尋或另一個 LLM 審稿呼叫。現有 Guard 遇到既有驗證失敗時仍可能條件式呼叫 LLM 修復；必要的劇本補查也可能增加該回合往返，這兩種情況不受「不固定加審稿」影響。

## Scenario Canon Boundary — CRITICAL（本期核心）

### 1. 不創造劇本內容

未由劇本材料支持，也未由 KP 明確建立或先前正式劇情事件確立的地點、房間、區域、NPC、敵人、生物、關鍵物品、線索、遭遇、通道等**會影響劇情或機制**的世界元素，Keeper 不得發明、添加、假定或暗示其存在。**「沒有寫」不等於「AI 可以合理補上」。**既有攜帶物規則允許合理的日常隨身小物；無機制效果的氣味、光線、聲響等感官細節也可描寫，但不能暗中構成新結構或證據，例如「牆後傳來骨骸碰撞聲」若等於創造地下室或敵人，就不屬於無害氣氛。

### 2. 地點

只有劇本明確描述／展示，或 KP／先前正式事件明確確立的地點才存在。不能因為建築常識或敘事方便生成地下室、閣樓、密道、隱藏房間等。玩家搜尋或試圖進入未成立的地點時，不得順勢產生該地點及其中的物件；若已確認劇本不存在該處，應清楚告知並在實際場景上結算行動。

### 3. 敵人與遭遇

戲劇張力、檢定失敗、玩家的恐懼、懷疑、提問或假設，都不能單獨生成敵人或戰鬥。敵人登場需要劇本當前條件支持，或 KP／先前正式事件已明確確立其存在。不得先由 Executor 加入敵人或開戰，再由 Narrator 替此行動編造理由。

### 4. 玩家假設與事實優先序

玩家說「我去地下室找骷髏」是行動意圖及假設，不是地下室與骷髏已存在的證據。當玩家期待或敘事合理性與劇本既定內容衝突時，以劇本為準。玩家行動成功也只能改變其實際能改變的狀態，不能反向補出未被授權的世界元素。

劇本給出的是世界基準；先前**已正式結算**的事件可改變當前狀態，例如劇本原本鎖住的門被玩家成功打開，後續敘事須依已開門的現況。KP Assistant 可明確改寫或新增設定，但要能辨識那是一條主持指令，不得從一般玩家話語或模型推測中推導出覆寫。這兩種情況都不是 AI 自行創作新劇本。

**「上回合 AI 說過」不等於新元素已成正典。**正式對話歷史是玩家聽過什麼的紀錄，可用來維持敘事連續性；但其中由模型自行生成、缺少劇本／KP／已結算事件依據的地點、敵人或線索，不能僅因文字已寫進 `state.log` 而取得權威地位。對話歷史與摘要可提示「曾說過什麼」，不單獨證明「世界中確實有什麼」。

### 既有敘事錯誤的連續性處理

最好在文字送出及狀態工具執行前避免越界；但若已公開錯誤敘事，不能下回合無聲否認，讓玩家看到前後矛盾。對已確認違反劇本正典且會影響玩家選擇的錯誤，應由 KP 明確確認，或在有充分權威來源時做一次清楚、簡短的玩家可見更正，指出前一句哪些內容不成立；不要把整段合理的氣氛描寫一起抹掉。若只是 RAG 沒找到來源，先標示無法確認，不得自行把已說內容判為不存在。

更正要有高於錯誤敘事的後續優先序，並讓近期歷史、`campaign_summary` 與 Memory RAG 在回想時看到「該句已更正」；不能只在當回合口頭改掉，後續又從舊摘要把密門或敵人找回來。現有 `state.log` 是純文字訊息，舊訊息會被濃縮成摘要與記憶；具體採「追加可追蹤的更正事件」「替摘要標記過期」或其他相容做法，須在實作設計時驗證，不能直接刪改玩家已看過的對話。若錯誤已觸發工具副作用（例如加了敵人、扣了 HP），單靠文字更正無法復原；必須由 KP 檢視權威狀態並明確修正或使用既有回溯能力，不可由 AI 偷偷重置。

### 玩家提出糾正（專用指令）

任何玩家都可指出 Keeper 先前敘事可能與劇本或已成立事件衝突，例如「剛才說有地下室，但這份劇本的平面圖沒有」。玩家的提報是**待核對的異議**，不直接創造、刪除或覆寫世界事實，也不應被意圖分類成新的探索／戰鬥行動而觸發工具副作用。

建議流程：

1. 玩家使用專用 `/coc correct` 指令，指明有問題的 Keeper 訊息或具體敘述並說明疑點；系統先確認收到。指令須在一般劇情訊息與意圖分類之前辨識，不能交給 Supervisor／Executor 當成角色行動，也不能觸發擲骰或遊戲狀態工具。建議優先支援回覆該則 Keeper 訊息並輸入 `/coc correct <疑點>`；若無法取得回覆參照，須明確提供訊息連結或 ID 與疑點。無法辨識目標時請玩家補充，不猜測其指向哪段敘事。只在有人提出異議時啟動核對，不為每一回合新增審稿呼叫。
2. 第一階段由 KP 核對當前劇本、權威地圖、已記錄的 KP 修正與已結算事件，並使用 `/coc correct approve <提報編號> <公開更正內容>` 或 `reject <提報編號>` 裁定。只有一次 RAG 未命中、證據互相矛盾或涉及劇本改編時，不得直接宣稱玩家說法正確。玩家可用 `withdraw <提報編號>` 撤回誤報；本期不自動發布更正。
3. 爭議尚未釐清時，不讓 Keeper 沿用被質疑的地點、敵人或線索推進**依賴它的**行動；其他不相關遊戲行動可繼續。若爭議涉及已執行工具或角色數值，交由 KP 檢視，不自動回溯或重骰。
4. 更正一旦確認，向所有看過錯誤敘事的玩家明確指出哪一句失效，保留原對話並追加具來源的更正紀錄；後續 prompt、摘要與 Memory RAG 必須以更正版本為準，避免舊說法反覆復活。若更正內容含秘密，只公開足以修正錯誤的部分，仍遵守劇透與隱私政策。

`app/commands/router.py` 在一般訊息之前分流 `correct`，Discord 回覆參照可傳入路由層；也接受明確訊息 ID 或連結。目標訊息由 KP 核對，提報本身不證明目標或內容正確。待核對紀錄獨立於 `state.log`；KP 核准時才加入玩家可見的更正及正式歷史。`app/agents/intent_router.py` 對一般玩家文字預設走 `GAMEPLAY_ACTION`，所以玩家直接說「你講錯了」不作為正式提報入口。

### 5. 缺少證據時的回覆

「已確認不存在」和「目前檢索片段沒有提到」必須區分。若完整可用劇本／權威地圖已確認無地下室，可直說沒有地下室；若只是單次 RAG 沒命中，回覆**「目前無法確認有這個地點」**，不得憑檢索缺口斷言它不存在，也不能創造它或繼續探索其內部。只有該事實會影響當前判定時，沿用現有 `EXECUTOR_SCENARIO_RAG_POLICY` 補查；補查仍無證據就維持無法確認。不能為了所有地點詢問而固定多做一次搜尋。

## 待確認的邊界範圍

### A. 劇本與既定事實

第一階段採用上面的嚴格劇本事實邊界。原草案允許「普通群眾反應」或無關主線的即興 NPC，與本次提供的 **任何 NPC 都需有來源** 要求衝突，已撤回該預設。可自由發揮的只剩不宣稱新世界元素的表述方式；是否允許劇本外次要人物，須另由 KP 明確授權。

### B. 玩家角色的決策權

Keeper 可描述玩家已宣告行動的可見後果及必要的即時反應，不可替玩家選擇目的地、接受交易、揭露私密動機、承諾下一步或自動完成尚待玩家決定的選項。NPC 可以主動行動，但不得用 NPC 隊友直接解完核心謎題或代玩家決定路線；這與 `docs/references/gameplay_style.md` 的既有角色定位一致。

### C. 場景與時間推進

每次回覆以當前行動及其直接後果為主。在玩家仍能回應的壓力點停下；跨場景、長時間跳躍、核心線索揭露或劇本章節切換須有明確觸發來源。`advance_scenario_chapter` 是 Context 視窗更新工具，不能把呼叫工具本身當作劇情已達成的證據。需討論哪些事件允許 Keeper 主動推進，哪些必須等玩家選擇或 KP 指令。

本期先處理 A。B、C 可用來避免敘事繞過 A，但不在這次規格修訂中擴成獨立功能。

## 候選設計

1. **最小提示詞補強**：在現有 Keeper／Executor／Narrator 提示詞旁加一段共用的 canon boundary，不覆寫現有 RAG 重用、劇情、防劇透與機制提示詞。提示詞需具體區分「玩家假設」與「已存在事實」、禁止憑失敗檢定生成敵人，並給出地下室例子；避免在每個 agent 重複一大段而增加 token 與延遲。
2. **沿用現有檢索路徑**：本回合已有足夠的劇本片段時直接重用；只有缺少會影響當前行動的具體事實才補查。不增加每回合固定 `search_scenario`、額外 LLM 驗證或第二次 Narrator 呼叫。檢索仍無法確認時，不能補造內容。
3. **在狀態變更前設邊界**：若實測顯示提示詞仍會讓 Executor 擅自 `start_combat`、`add_npc_to_combat` 或建立重要事實，評估在對應工具入口檢查來源及當前條件。僅靠 Narrator 事後改字無法處理已落庫的副作用；不能用沒有證據的通用「世界元素偵測器」直接阻擋所有工具。
4. **在敘事輸出前核對**：若仍出現文字憑空創造地點或敵人，評估是否有足夠結構化資訊做低成本檢查；沒有可靠依據時先保留未知或使用中性回覆，不設每回合額外 LLM 審稿。
5. **兼顧兩條路徑**：Agentic Supervisor 與仍在使用的 `keeper.run_turn` 應套用同一政策定義；KP Assistant 的明確主持修正可新增／覆蓋事實，但應保留來源與範圍，不由一般玩家話語冒充。

第一階段優先低成本提示詞補強與真實案例驗證；若無法守住，再依具體失敗點補工具前置檢查或輸出檢查。純關鍵字無法可靠辨識「世界元素是否由劇本授權」，不列為唯一防線。

## 資料結構與相容性

`GroupState.narrative_corrections` 保存獨立的提報紀錄，包括目標訊息、疑點、提報者、狀態、時間與 KP 的公開更正。舊存檔沒有此欄位時預設空清單。已核准的更正每輪以高於舊摘要及 Memory RAG 的規則注入共用提示詞，不直接刪改玩家看過的舊訊息；若已改變角色數值或其他權威狀態，仍須 KP 另外檢視回溯或修正。`established_facts`、`known_clues` 與工具來源檢查屬實際情境測試後的第二階段候選，不能把舊劇情文字無條件升格為權威事實。

現有 `docs/keeper_skill.md` 容許玩家帶有未登記但合理的日常小物，亦要求 Keeper 主動用既有 NPC 意圖和環境變化維持張力。使用者已確認保留日常小物及不影響劇情／機制的感官細節；例如普通筆、手帕、雨聲可依既有規則出現，但武器、解謎道具、逃生通道、敵人蹤跡與新線索不能藉「細節」名義補出。物品是否合理仍由現有年代、來源、負擔能力及合法性規則判斷；本規格不取代那些規則。

## 非目標

- 不在每回合固定新增 RAG 查詢、LLM 審稿或第二次 Narrator 呼叫。
- 不重設 `SPOILER_PROTECTION_ENABLED`／`PRIVACY_ISOLATION_ENABLED` 的意義。
- 不讓自動審稿器替 KP 決定唯一合法劇情；KP Assistant 仍是主持層的明確覆寫來源。
- 不要求所有日常敘事細節都先記錄為結構化事實。

## 驗證計畫

- 具體輸入、權威材料與期望結果列在 [劇情邊界情境測試案例](narrative_boundaries_eval_cases.md)；提示詞單元測試只驗證政策有進入各執行路徑，仍需用實際回合檢驗模型敘事與工具副作用。
- 收集至少數個「本來應允許」與「確實越界」的真實回合，標記原始輸入、劇本可用片段、當時狀態、工具呼叫、輸出及期望的停點。優先包括「玩家找不存在的地下室／骷髏」「失敗檢定憑空冒出敵人」「NPC／線索由玩家猜測變成事實」。
- 覆蓋：普通感官描寫、NPC 合理反應、未揭露線索、玩家尚未決定的選項、場景轉換、KP 明確改寫設定，以及沒有劇本可查的自由場次。
- 分別驗證 Agentic 與舊版 Keeper 路徑；若涉及工具前置檢查，確認被拒絕時沒有部分狀態更新；若涉及輸出重寫，確認正式歷史只保存最終送出的文字。
- 模擬錯誤地點已公開、玩家已據此行動，以及舊訊息已進 `campaign_summary`／Memory RAG 的情況：更正後的下一輪不能重新宣稱該地點存在；已發生的玩家行動與工具副作用要分別處理，不靠刪除對話掩蓋。
- 模擬玩家正確提報、錯誤提報、單次 RAG 無結果、已由 KP 改編劇本、多人在異議期間接續行動，以及涉劇透的更正；確認 `/coc correct` 在一般劇情訊息前分流，提報本身不進入 Supervisor／Executor、不擲骰、不觸發遊戲工具，待裁定內容不能成為新正典，確認後只有受影響的敘事與狀態被修正。另驗證回覆參照、明確訊息 ID、缺少或無效目標及重複送出指令的處理。
- 比較修訂前後的工具呼叫次數、RAG 查詢次數、模型 iteration、額外 token 與回合延遲；不接受靠每回合多一輪 LLM 呼叫才達到的修正。並記錄越界率與誤擋率，再決定是否需要第二階段防線。

## 討論決策

1. **已決定：**單次 RAG 未命中時說目前無法確認，必要時補查；只有確定不存在才明說不存在。實作驗證仍需確認哪些資料可構成充分的負面證據。
2. **已決定：**合理的日常隨身小物與無劇情／機制效果的感官細節沿用既有規則；禁止補出會影響劇情或機制的內容。
3. KP Assistant 的主持指令若與劇本衝突，是否可即時覆寫？若可，如何標明這是明確改編而非 AI 自行推翻劇本？
4. 不固定增加每回合 LLM 審稿的前提下，哪幾個真實案例最值得做對照試驗，判定提示詞補強是否足夠？
5. **已決定：**本期由 KP 明確確認並發布更正，不讓 AI 單憑一次 RAG 命中或未命中自行裁定。
6. **已決定：**玩家提報使用專用 `/coc correct`，於一般劇情訊息之前分流。可回覆目標訊息，或明確提供訊息 ID／連結；不把一般玩家話語當成提報指令。
