# 設計規格草案：劇情敘事邊界

## 文件狀態

討論稿，尚未決定「邊界」的優先範圍，也沒有程式實作。工作分支：`enhancement/narrative-boundaries-spec`，整合目標：`main_v2`。本文先記錄目前系統的控制點、可選的產品規則與驗證方法；選定範圍後，再把草案收斂為可實作的契約。

## 問題與目標

Keeper 必須能描寫環境、扮演 NPC、回應玩家行動並維持懸疑，但不能把敘事生成誤當成已成立的世界事實。需要定義：哪些細節可由 Keeper 即興補足、哪些變更需要劇本或已確立事實支持、哪些決定須留給玩家，以及何時才可推進到下一場景。

目標是讓玩家每輪看見有反應的場景，同時可追溯重大劇情變化的來源。這份工作聚焦「敘事內容與世界事實的邊界」，不重做骰子、戰鬥或隱私政策。

## 現況與缺口

- `app/services/prompt_config.py` 的 Narrator 指令已要求依劇本與機制結果敘述，禁止隨意發明關鍵線索、NPC、地點或真相。`docs/keeper_skill.md` 也要求一次只推進一個場景片段。
- `app/agents/narrator.py` 沒有工具，收到劇本／記憶脈絡、權威角色狀態及 Executor 的結果後生成回覆。`app/agents/supervisor.py` 隨後依序執行 Guard、劇透字詞掃描及檢定一致性修正，才將回合文字寫入正式歷史。
- `app/agents/rule_validator.py` 的確定性驗證只抓系統外洩字眼與未閉合的 Markdown；`app/spoiler_policy.py` 的公開回覆掃描只對已收集到的敏感字詞做字面比對。這些檢查無法可靠判斷「擅自新增重要 NPC」「替玩家決定下一步」或「尚未達成條件卻跳場景」。
- Executor 的工具可能在 Narrator 輸出前已改動權威狀態。若只在最終文字上設防，無法撤銷已執行的工具副作用。舊版 `app/keeper.py` 單一 Keeper 路徑也會產生公開敘事，不能只涵蓋 Agentic Supervisor。
- 現有劇透防護處理「何時公開秘密」，但「能否宣稱一件新事情已發生」還需要另一份規則；兩者應共用事實來源，不應把所有新描述一律視為劇透。

## 待確認的邊界範圍

### A. 劇本與既定事實

重大事實只能來自目前可用劇本內容、已記錄的公開／私人事實、已完成的機制結果，或 KP Assistant 的明確主持指令。Keeper 可以補感官細節、普通群眾反應與不改變調查結構的對話；不能憑空宣布新核心線索、真相、關鍵 NPC 身分、重要地點或劇本未授權的重大事件。資料不足時保留未知，或用 NPC 的不確定說法呈現推測，不將推測寫成權威事實。

### B. 玩家角色的決策權

Keeper 可描述玩家已宣告行動的可見後果及必要的即時反應，不可替玩家選擇目的地、接受交易、揭露私密動機、承諾下一步或自動完成尚待玩家決定的選項。NPC 可以主動行動，但不得用 NPC 隊友直接解完核心謎題或代玩家決定路線；這與 `docs/references/gameplay_style.md` 的既有角色定位一致。

### C. 場景與時間推進

每次回覆以當前行動及其直接後果為主。在玩家仍能回應的壓力點停下；跨場景、長時間跳躍、核心線索揭露或劇本章節切換須有明確觸發來源。`advance_scenario_chapter` 是 Context 視窗更新工具，不能把呼叫工具本身當作劇情已達成的證據。需討論哪些事件允許 Keeper 主動推進，哪些必須等玩家選擇或 KP 指令。

上述三項是候選規則，並非已同意全部實作。可先選一項做第一階段。

## 候選設計

1. **先建立事件分類**：每個回合把「可自由描寫的表層細節」與「會改變權威世界狀態的事件」分開。重大事件需附來源類型（劇本、既定事實、機制結果、玩家行動、KP 指令）及其識別資訊。若只是 NPC 的猜測，標成猜測，不能進入 `established_facts`。
2. **在動作發生前設邊界**：Executor 準備呼叫會改變劇情狀態的工具時，檢查來源與當前條件。僅靠 Narrator 事後改字無法處理已落庫的變更；工具前置檢查須與輸出檢查分工。
3. **在敘事輸出前核對**：Narrator 可看見本回合允許成立的事件摘要。公開回覆若額外宣稱重大事件，可要求重寫或使用不新增事實的中性回覆；驗證方式需先以真實失敗案例評估，避免把正常氣氛描寫大量誤判。
4. **兼顧兩條路徑**：Agentic Supervisor 與仍在使用的 `keeper.run_turn` 應套用同一政策定義；KP Assistant 的明確主持修正可新增／覆蓋事實，但應保留來源與範圍，不由一般玩家話語冒充。

目前不選定「新增 LLM 審稿器」或「純關鍵字規則」作為唯一實作。前者增加延遲且判斷可能不穩；後者對語意事件的辨識力不足。先蒐集具體錯誤回合，確認哪個邊界最常失守，再決定最小的可靠檢查點。

## 資料結構與相容性

討論稿不新增資料庫欄位。若採事件分類，優先評估沿用 `GroupState.established_facts`、`known_clues`、現有工具結果與正式回合紀錄；是否需要另存事件來源、是否需要標示「推測／已確立／已揭露」，須由具體案例決定。不能把舊劇情文字無條件升格為權威事實，也不能以新規則改寫既有存檔或玩家角色數值。

## 非目標

- 不在本分支修改 runtime、提示詞、工具 schema 或資料表。
- 不重設 `SPOILER_PROTECTION_ENABLED`／`PRIVACY_ISOLATION_ENABLED` 的意義。
- 不讓自動審稿器替 KP 決定唯一合法劇情；KP Assistant 仍是主持層的明確覆寫來源。
- 不要求所有日常敘事細節都先記錄為結構化事實。

## 驗證計畫

- 收集至少數個「本來應允許」與「確實越界」的真實回合，標記原始輸入、劇本可用片段、當時狀態、工具呼叫、輸出及期望的停點。
- 覆蓋：普通感官描寫、NPC 合理反應、未揭露線索、玩家尚未決定的選項、場景轉換、KP 明確改寫設定，以及沒有劇本可查的自由場次。
- 分別驗證 Agentic 與舊版 Keeper 路徑；若涉及工具前置檢查，確認被拒絕時沒有部分狀態更新；若涉及輸出重寫，確認正式歷史只保存最終送出的文字。
- 觀察誤擋率、額外模型呼叫與回合延遲，再決定是否進入實作。

## 討論決策

1. 第一階段最需要的「邊界」是 A 劇本／事實、B 玩家決策權，還是 C 場景推進？可選多項，但需要實際越界例子決定優先順序。
2. 即興新增次要 NPC、環境事件與支線線索的允許程度為何？哪些必須先讓 KP 核准？
3. KP Assistant 的主持指令是否可在進行中的場景即時覆寫劇本設定？若可以，要如何記錄覆寫來源與影響範圍？
4. 當劇本片段缺失或 RAG 查不到時，偏好保留未知、向 KP 詢問、還是容許可回滾的臨時設定？
