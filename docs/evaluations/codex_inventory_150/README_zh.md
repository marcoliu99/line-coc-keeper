# Codex 150 輪穩定性測試

日期 2026-09-28；程式版本 `90f0299`。Codex CLI 0.157.1、gpt-6-luna、
medium reasoning；exec 與 app-server 各 75 案例。每組重複五種場景
15 次：待擲時拾取、一般拾取、保留原檢定、成功檢定後續、失敗檢定後續。
整批測試期間不修改 runtime。

使用真實 ChatGPT OAuth 與既有 Supervisor 流程，資料是隔離的合成場景，
Python 骰點固定；沒有正式遊戲狀態或 Discord 訊息。這不涵蓋整場長團、
即時 RAG、任意戰鬥、真實多人併發或所有敘事內容。

兩個程序共用 OAuth 容量，耗時僅為描述性數據。一個案例包含必要的玩家
檢定提交與後續敘事，所以案例數不等於模型請求數。失敗全部保留，不用
重跑成功結果取代。JSONL 保留決策、工具收據與裁決結果，省略重複 prompt。

## 指標

- 流程：通過場景狀態與敘事斷言。
- 工具：預期工具／參數與成功收據，沒有額外非預期工具或被 Python
  拒絕的無效提案。安全擋住仍算工具錯誤。
- 首次通過：流程與工具通過，且没有未完成重試或裁決修復。
- 修復、模型請求、實際工具、Python 擲骰與耗時分開記錄；修復後成功
  不會算成首次通過。

## 已觀察到的缺陷

- app-server 第 7、13 組，待擲拾取：尚未呼叫工具，卻引用不存在的 tool:1
  並聲稱已取得鑰匙。Python 拒絕引用後，裁決回饋使模型補做一次
  add_carried_item 並交回有效等待裁決。這是修復成功，不是首次正確。
- app-server 第 8 組，保留檢定：玩家只重申文件行動，模型卻呼叫
  add_carried_item 取得劇本裡的鑰匙，背包真的改變。pending 不變，
  await_check 因而通過。工具指標有正確抓到失敗；此案例的流程斷言
  只檢查 pending／洩漏線索，漏查背包不變，因此整體通過必須同時要求
  「流程與工具」通過，不能只報流程數字。
- app-server 第 10 組，待擲拾取：完全沒有呼叫背包工具，只以原 check_id
  與 state 交回 await_check，並承認拾取沒有成功收據。Python 接受原
  pending 身分，未觸發修復。背包斷言抓到鑰匙未取得。

剩餘缺口是「玩家本次要求」與「實際變更」的對應。劇本有物品不代表
玩家要求拿取；pending 身分正確，也不代表新增的獨立操作已完成。
現有裁決回饋只有在驗證器拒絕時才有效，無法修復被驗證器接受的漏操作。

後續應將要求的行動、允許的狀態變更與已核對的效果連起來，區分已完成
的獨立操作與仍待處理的檢定，並補強純等待案例的背包不變斷言。完全
相同的 pending 重複行動可保守限制為唯讀工具；更廣的自然語言意圖需
有依據的行動契約，不能只靠臨時關鍵字比對。不可放寬收據驗證，也不能
讓 Python 猜測並自動取得物品。本批固定版本測試不包含 runtime 修正。

待擲拾取最終 29/30、首次 27/30；純等待 29/30；一般拾取、成功檢定、失敗檢定各 30/30。原始流程斷言為 149/150，但含一筆被工具斷言抓到的額外拾取，所以不以此數字當整體成功率。

前次 25/25 無法代表低頻錯誤已消失；此次放大樣本實際發現兩項未修復缺陷。建議維持目前 exec 設定，先補行動與效果驗證再評估 app-server；75/75 也不構成普遍零錯誤保證。
