Supervisor 場景與固定 Python 骰點，沒有正式資料或 Discord 訊息。
exec 三次重複共 15 案例，app-server 兩次重複共 10 案例；兩組皆為

## 原因與修正

前一批 18 案例中，exec 兩次 add_carried_item 已成功，卻交回
resolved_without_check。Python 因原檢定仍待擲而拒絕，但驗證發生在
Executor 結束後，模型沒有收到拒絕原因，也無法使用既有收據更正交接。
app-server 另一次把「劇本允許拿取」當成「已實際拿取」，未送出背包工具。

這次明確區分：劇本允許 → 工具執行並驗證背包 → 回報仍待處理的檢定。
獨立操作成功後，使用原 check_id 加本次工具收據交回 await_check；不能
只套用等待候選而漏做本次要求，也不能把尚有 pending 說成整回合完成。

Codex 的決策迴圈另加入最多一次既有 Python 裁決驗證回饋。已成功工具
不得重做；不自動改背包、不放寬驗證、不增加固定 LLM 審稿。最後結果
仍經原驗證器核對。其他 provider 不變。原本「未送工具就回未完成」的
一次重試仍獨立計數，兩者共用既有期限、迭代與工具預算；需要補工具時
修復可能增加一輪以上模型往返。

整合測試重現兩種錯誤，走真實 Supervisor、Executor 與背包 gateway，
確認原 pending 不變、物品只加入一次、沒有擲骰，且最後裁決被接受。
另測重試上限、真正卡點與已提交工具不重播。

## 指標與限制

統計見下表與 summary.json。一次案例包含必要的檢定提交與後續敘事，
因此 25 案例不等於 25 次模型請求。首次通過排除被拒提案、未完成重試
與裁決修復；完整流程還需通過場景狀態與敘事斷言。工具正確率要求預期
工具／參數與成功收據，不接受額外非預期呼叫或被擋的無效提案。

JSONL 保留合成決策、工具收據與驗證碼，省略重複的動態 prompt。所有
失敗均保留，前一批 18 案例報告不改寫。這些小型場景不能證明整場團務
與所有自然語言敘事都正確。重現指令見 [英文版](README.md)。
